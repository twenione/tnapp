## D-001. 이탈 임계값 네임스페이스 분리

**상태**: 확정 | **일자**: 2026-09-13

### 배경

두 문서가 같은 이름으로 다른 값을 쓰고 있었다.

```
로깅 스킬 §6 / session_schema tags   OFF_ROUTE = 30m + 60초
MVP 계획 §4.1                        진입 25m/20초, 해제 15m/10초
```

오류가 아니라 용도가 다른 값이다. 그러나 이름이 같으면 구현 에이전트가 반드시 하나로 통합하려 든다.

### 결정

네임스페이스를 분리한다. 값은 서로 독립이며 튜닝도 따로 한다.

```
guide.offRoute.*        실시간 안내용
  enterDist 25m / enterDwell 20s
  exitDist  15m / exitDwell  10s
  근거: 사용자 체감 기준. 늦게 알리면 이미 멀리 간 뒤다

tagging.OFF_ROUTE.*     사후 태깅용
  dist 30m / dwell 60s
  근거: 관심 구간 과다 생성 방지. 보수적으로 둔다
```

### 시행

- 엔진 config와 태거 config를 분리된 키로 둔다
- 두 값 모두 코드 상수 금지. config에서 읽는다 (로깅 스킬 §6)

## D-002. 반증 테스트 용어 교체

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 §2.2, §4(4)가 **음성(陰性) 대조 = negative control**을 요구한다. 검사기가 통과시키는 것만 확인하면 아무것도 검사하지 않는 검사기와 구별되지 않으므로, 고의 위반을 주입해 실제로 기각되는지 확인하라는 규율이다.

문제는 용어다. 이 프로젝트는 TTS 음성 안내가 핵심 기능이고, 로그에 `tts`·`stt` 스트림이 있으며, 문서 전반에 "음성 안내", "발화"가 나온다. 그 한가운데 "음성 대조"를 놓으면 구현 에이전트가 **TTS 출력 비교 작업**으로 오해할 소지가 크다. 실제로 "기록된 발화와 리플레이 발화를 대조한다"는 작업이 이 프로젝트에 실재하므로, 그럴듯한 오해다.

### 결정

```
음성 대조  →  반증 테스트 (negative control)
```

관리 지시서 §2.2, §4(4) 두 곳. 이후 모든 문서에서 "반증 테스트"로 통일한다.

### 근거

설계 변경이 아니라 지시가 오독될 여지를 막는 수정이다. 오독되면 검증 체계 전체가 헛돈다.

## D-003. 검증 계층 공백 — 판정 주체를 기계로 이전

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 §4는 구현 에이전트의 보고를 5개 요건으로 검증한다. 그러나 **검증 에이전트의 판정 자체를 검증할 주체가 없다.**

```
구현 에이전트 → 보고 → 검증 에이전트 → 판정 → ???
```

검증 에이전트가 "반증 테스트 완료, exit 1 확인"이라고 쓰면 그것을 확인할 방법이 없다. §4(3)이 경고한 사고 — 검사 하네스가 자기 입력을 매칭하고 "확인됨"으로 보고한 일 — 가 한 층 위에서 재현될 수 있다.

상위 감사자를 계속 쌓는 것은 해가 아니다. 무한히 올라간다. 사람이 매번 감사하는 방식도 실패한다 — 로깅 가이드 §1.1이 이미 적었다. 자발적 기록과 사람 의존 규율은 반드시 중단된다.

### 결정

감사 계층을 늘리지 않는다. **검증 에이전트가 주관적으로 판정하던 항목을 CI로 옮겨 판정 주체를 기계로 바꾼다.**

#### D-003a. 반증 테스트를 CI 잡으로

수동 수행 + 보고 방식을 폐기한다. 고의 위반 픽스처를 저장소에 두고 CI가 매번 돌린다.

```
testdata/violations/
  engine_impure_clock.kt.txt      System.currentTimeMillis() 포함
  engine_impure_random.kt.txt     Math.random() 포함
  session_seq_regress/            seq 역행
  session_missing_manifest/       매니페스트 누락

guard.yml 잡 추가: negative-control
  각 픽스처에 검사기를 돌려 exit 1 을 확인
  exit 0 이면 이 잡이 실패한다
```

픽스처는 컴파일 대상에서 제외한다(`.kt.txt` 확장자). 빌드가 깨지면 안 된다.

#### D-003b. 리플레이 자기 대조를 CI 잡으로

```
guard.yml 잡 추가: replay-determinism
  동일 세션을 2회 리플레이해 서로 비교
  불일치 = 비결정성 확정
```

기록과 비교하는 기존 `replay` 잡은 기록 자체가 오염됐으면 통과한다. 자기 자신과 비교하는 방식은 그 구멍이 없다.

정적 순수성 검사는 래퍼 경유 간접 호출을 잡지 못한다(관리 지시서 §2.1이 이미 인정). **진짜 판정기는 리플레이다.** 정적 검사는 1차 필터로 남긴다.

작동 조건: 골든 세션 1개로는 부족하다. 시계·난수 의존은 특정 조건에서만 드러난다. 합성 세션(노이즈 3단계 × 이탈 3종)을 전부 대상에 넣는다.

#### D-003c. 필수 상태 체크를 5개로

```
purity
session-format
replay
negative-control      ← 추가
replay-determinism    ← 추가
```

#### D-003d. 검증 에이전트에게 남는 것

```
남는 것   보고와 커밋 SHA 대조
          구현이 검사를 우회하는 방향으로 가는지 판단
          엔진 패키지 경계 감시
          게이트 통과 판정

빠지는 것  검사기가 작동하는지 확인 → CI가 한다
```

검증 에이전트의 신뢰성을 높이는 것보다, **신뢰받아야 할 범위를 줄이는 편이 확실하다.**

#### D-003e. 판단 영역은 숫자 추이로 노출

경계 감시는 여전히 사람/에이전트 판단이다. 서술이 아니라 지표로 보고하게 한다. 관리 지시서 §8 주기 보고에 추가한다.

```
엔진 패키지 파일 수 / LOC
엔진 외부 헬퍼 LOC (엔진이 호출하는 유틸)
```

엔진 LOC가 줄면서 외부 헬퍼가 늘면 **경계를 밖으로 밀어낸 것**이다. 정적 검사가 못 잡는 우회의 대리 지표다. 서술로는 숨길 수 있으나 숫자 추이는 숨기기 어렵다.

#### D-003f. 소유자 감사는 조건부

매번 감사는 지속되지 않는다. 세 조건에서만 확인을 요청한다.

```
필수 체크를 해제·완화하려 할 때 (지시서 §5 "푸는 변경")
게이트 통과 선언 시점 (G0~G3, 4회)
검사기가 잡은 위반 건수가 4주 연속 0일 때
```

마지막 항목이 §8의 "0이면 검사기를 의심한다"를 실행 가능한 트리거로 바꾼 것이다.

### 부작용

G0 작업량이 늘어난다. 픽스처 4종 + CI 잡 2개. 전부 코드 0줄일 때 만드는 것이라 지금이 가장 싸다.

## D-004. 세션 스키마 v1 동결 범위 한정

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 G2는 실제 산행 1회 후 스키마를 v1으로 동결한다고 한다. 그런데 `session_schema.json` v0에는 `ar`, `stt` 스트림이 이미 정의되어 있고, MVP 계획상 AR 화살표는 Phase 4, STT는 범위 밖이다.

즉 **v1 동결 시점에 `ar`·`stt`는 한 번도 실측되지 않은 채 동결된다.** 로깅 스킬 §8.1의 "실측 없이 스키마를 정교하게 만들지 않는다"와 정면으로 어긋난다.

### 결정

```
동결 대상    manifest, event_envelope, loc, guide, sys, err
미동결 유지  imu, baro, ar, stt   ← "실험 스트림"으로 명시
```

실험 스트림은 `validate_session.py` 필수 검사 대상에서 제외한다.

### 근거

리플레이가 대조하는 것은 `guide` 스트림뿐이다. 나머지는 입력이거나 부수 기록이므로 전부 동결할 이유가 없다. 실측되지 않은 스트림을 동결하면 추측을 규격으로 굳히게 된다.

## D-005. AKB 공급 계약 확정

**상태**: 확정 | **일자**: 2026-09-13
**근거 문서**: `xchg/akb-tnapp/XCHG-001`, `XCHG-002`, `XCHG-003`

### 결정

AKB 총괄 요청 4건을 전부 수용했다. 계약이 성립했다.

```
공급   빌드 실패 레코드 / 실패↔수정 쌍 / 검사기 기각 이력
비제공 런타임 산행 세션 로그 / 안전 사건 기록 / AKB 형식 가공
조건   단방향, 통지 의무 없음, tnApp 단독 중단권, 범위 한정
```

### 수용한 확장 4건

| 항목 | 내용 | 비용 |
|---|---|---|
| `runner_image_version` | 러너 환경변수 그대로 | 필드 1 |
| `schema_version` | `failrec-` 접두. 소비 측 자력 감지용 | 필드 1 |
| 커밋 원자성 | Failed-Run 커밋에 다른 변경 혼입 금지 | 리뷰 규칙 |
| 해소 확인 기록 | 수정 후 실제 통과 증거 | 필드 4 + CI 스텝 1 |

### 해소 확인 기록 — 구현 방식 변경

AKB 제안(실패 시점에서 후속 성공 추적)은 `workflow_run` 트리거 구조상 상태 보유나 역방향 조회가 필요하다. **성공 시점에서 뒤를 보는 방향으로 뒤집는다.**

```
guard 성공 시
  HEAD 커밋에 Failed-Run: 트레일러가 있는가
  있으면 → 실패 레코드에 해소 레코드를 append (원본 수정 아님)
    resolved_by_commit / resolved_run_id / resolved_at
```

`check_commit_trailer.py`의 트레일러 파싱을 재사용한다.

**이 결정은 AKB를 위한 것만이 아니다.** 관리 지시서 §4는 구현 에이전트에게 "실제로 실행됐다는 증거"를 요구하면서, 정작 수정이 실패를 해소했다는 증거는 요구하지 않았다. AKB 요청이 tnApp 자신의 규율 공백을 짚었다.

**부수 효과**: 해소 필드가 끝내 채워지지 않은 레코드가 남는다. "고쳤다고 커밋했으나 통과하지 못한" 사례가 별도 작업 없이 분리된다.

### error_signature — 정규화하지 않는다

원문 보존. 정규화·마스킹·해시는 소비 시점 처리. 정규화가 비가역이며, D1에서 재설계가 가능했던 유일한 이유가 원문 보존이었다는 AKB 근거를 수용했다.

예외는 비밀정보 마스킹뿐이며, `masking_ruleset_version`을 함께 기록한다. 마스킹도 비가역이므로 어떤 비가역 처리가 가해졌는지는 남겨야 한다.

### 향후 범위 확대 시 우선 검토 항목

**`negative-control` 픽스처를 AKB 홀드아웃 재료로 제공하는 안.**

AKB D1에서 `pathological` 사례가 530건 중 0건이었고 야생에 존재하지 않는 종류라면, 통제된 환경에서 의도적으로 만드는 것 외에 경로가 없다. D-003a의 픽스처가 그 성격에 가깝다 — 고의 주입 위반이며, 검사기가 기각해야 정상인 사례다.

**이번 계약에 포함하지 않는다.** AKB가 별도 문서로 제기하면 검토한다.

### AKB 재개 미정 상태에 대한 판단

AKB S0-R은 2026-09-13 미도달 종료, 재개 미정이다. 이를 인지하고 수용했다.

```

tnApp에도 필요했다   해소 확인 기록은 자체 규율 공백이었다
소급이 불가능하다    지금 넣지 않으면 6개월 뒤에도 없다
```

## 이 문서가 분리된 이유

드라이브는 기존 파일에 append가 불가능합니다. 매번 전체를 다시 올리면 append-only 원칙이 형식만 남으므로, 분책으로 처리합니다.

**저장소에 `docs/DECISIONS.md`가 만들어지면 두 문서를 병합해 이관합니다.** git이 append-only를 구조적으로 보장하고, force push 금지가 걸려 있어 소급 수정도 막힙니다. 드라이브 사본은 그 시점부터 참조용입니다.

## D-006. 저장소 및 자격증명 구성

```
1순위  브랜치 보호가 실제로 작동할 것
2순위  프라이빗
```

```
ruleset   main-protection (id 23165335), enforcement active
bypass_actors   비어 있음. current_user_can_bypass: never
rules   deletion / non_fast_forward / pull_request
pull_request 파라미터
  required_approving_review_count: 0
    → 1인 개발 구조. GitHub 은 작성자가 자기 PR 을 승인할 수 없으므로

```

**bypass 목록을 비워둔 것이 핵심입니다.** admin 을 bypass 에 넣으면 force push 차단 검증이 통과해버립니다 — 검사기가 자기를 통과시키는 것과 같습니다.

/sessions/

```

`.gitignore`는 실수를 막을 뿐이며 `git add -f`로 우회됩니다. 규율이 함께 필요합니다.

### PAT

```

  종류    Fine-grained PAT
  대상    tnapp-failure-log 단일
  권한    Contents: Read and write (+ Metadata: Read-only, 자동)

퍼블릭 저장소이므로 포크 PR이 들어올 수 있습니다. `workflow_run` 트리거 잡은 시크릿과 쓰기 권한을 가진 채 base 컨텍스트에서 실행됩니다.

```

## D-007. TASK-000 판정 기준 정정 — 실패와 수행 불가의 구분

**상태**: 확정 | **일자**: 2026-09-13

TASK-000 지시서 §6은 "4.4(force push 반증 테스트) 실패는 단독으로 착수 불가"라고 규정했습니다. **실패와 수행 불가를 구분하지 않은 지시서의 결함입니다.**

```
실패       force push 를 시도했는데 성공했다 → 보호 미작동. 착수 불가
수행 불가   main 브랜치가 없어 시도 자체를 못 했다 → 정보 없음
```

빈 저장소에 main이 없는 것은 당연하며, main은 최초 커밋으로 생기고, 최초 커밋은 G0 작업의 일부입니다. 착수 전 관문으로 두면 순환이 되어 영원히 착수할 수 없습니다.

**4.4는 로드맵 §3.4-2(G0 완료 판정)의 원위치로 되돌립니다.**

점검 에이전트가 이 충돌을 임의 해석하지 않고 그대로 보고한 것은 올바른 처리였습니다.

## D-008. 인증 확보 후에도 점검 에이전트는 읽기 전용

## D-009. 커밋 이메일 — noreply 주소 사용

**상태**: 확정 | **일자**: 2026-09-13

브랜치 보호의 `require_extra_approval_for_unattributed_changes`가 기본값 `true`로 설정되어 있습니다. GitHub 계정에 연결되지 않은 커밋이 PR에 포함되면 추가 승인을 요구하며, 승인 수가 0이어도 발동합니다.

```
git config user.email "<ID>+twenione@users.noreply.github.com"
```

noreply 주소는 정의상 계정에 연결되어 있으므로 이 조건이 발생하지 않습니다. 실제 이메일을 공개 저장소의 커밋 이력에 남기지 않는 부수 이득도 있습니다.

**규칙 파라미터를 끄는 방안은 채택하지 않았습니다.** 실제로 막히는지 확인되지도 않은 상태에서 규칙부터 푸는 것은 순서가 틀렸고, 푸는 변경은 관리 지시서 §5 대상입니다.

## D-011. 현장 테스트를 G2-a / G2-b로 분리

**상태**: 확정 | **일자**: 2026-09-13

실제 산행은 3시간 이상이 소요되어 개발 루프에 넣을 수 없습니다. 소유자가 자택 인근에 테스트 경로를 확보했으며, 갈림길이 복수 존재합니다.

```
G2-a  동네 경로 테스트
      기능 동작 확인, 서비스 생존, 배터리 실측, UI 조작성
      반복 가능. 개발 루프에 포함

G2-b  실제 산행 1회
      GPS 품질 실측, 파라미터 검증
      스키마 v1 동결 조건
```

### 동네 테스트로 검증되지 않는 것

```
수목 밀집 구간 GPS 품질 (이 앱의 난이도 대부분이 여기 있다)
계곡 · 능선 사면의 멀티패스
통신 두절 상태
철 성분 암반에 의한 나침반 오차
```

**따라서 동네 테스트로 파라미터를 튜닝하지 않습니다.** 개활지에서는 오차가 5m 안쪽으로 나오므로 이탈 임계 25m가 과해 보이고 줄이고 싶어집니다. 그 상태로 산에 가면 오탐이 쏟아집니다.

스키마 동결을 G2-b에 묶어두는 이유도 같습니다. 동네 데이터만 보고 굳히면 산에서 필요한 필드를 놓칩니다.

### 기준 경로 고정

같은 경로를 반복해 걷는 것이 전제입니다. 매번 다른 곳을 걸으면 회차 간 비교가 불가능합니다. 세션 로그의 `gpx_hash`가 경로 동일성을 보장합니다 — 경로 파일이 바뀌면 해시가 달라지므로 다른 경로의 결과를 섞어 비교하는 실수가 걸러집니다.

### 분기점 사전 기록

테스트 판정을 위해 소유자가 분기점 목록을 사전 작성합니다.

```
위치 / 분기 각도(눈대중) / 정답 방향 / 형태
형태 = 꺾임형(정답이 꺾임) 또는 직진형(정답이 직진, 옆길이 갈라짐)
```

**직진형 분기는 GPX상 방위각 변화가 0이므로 꺾임 예고가 원리적으로 불가능합니다.** 사전 분류하지 않으면 테스트에서 이를 결함으로 오인 보고하게 됩니다. 알려진 한계이며, 이탈 감지 성능 실측에 사용합니다.

## D-013. 필수 상태 체크를 6개로 — `commit-trailer` 포함

## D-014. 해소 레코드 `run_id`는 원본 실패의 ID

**상태**: 확정 | **일자**: 2026-09-13
**근거**: `TASK-003_DECISION_REQUEST_2026-09-13.md` D-R9

### 상황

PR #9 병합 후 생성된 해소 레코드 3건 전부에서 `run_id`가 `resolved_run_id`와 동일한 값이었습니다. 원본 실패 run(`34761334020`, `34761342131`)은 해소 레코드 어디에도 나타나지 않습니다.

### 결정 — 점검 의견 (a) 채택. 현행 구현은 사양 위반입니다

스키마 설명이 부실했던 것은 총괄 책임이나, 필드 의미는 원래 (a)였습니다.

```
run_id               해소된 원본 실패의 run_id
resolved_by_commit   수정 커밋 SHA
resolved_run_id      해소를 확정한 성공 run 의 id
resolved_at          타임스탬프
```

**근거 1 — 스키마 구조.** `resolved_` 접두가 붙은 세 필드가 "해소 쪽" 정보이고, 접두 없는 `run_id`는 그 대칭으로 "해소된 쪽"입니다. 접두를 붙인 이유가 그것 외에 없습니다. 현행 구현에서는 두 필드가 항상 같으므로 하나가 순수한 중복입니다.

**근거 2 — AKB 계약 구조.** AKB는 `tnapp-failure-log`만 읽습니다. 앱 저장소의 커밋 메시지를 조회할 권한이 계약에 없습니다. `resolved_by_commit`에서 트레일러를 역추적하려면 두 저장소를 모두 봐야 하는데, **단방향 읽기 계약에서 그것이 성립하지 않습니다.** 레코드만으로 연결이 닫혀야 합니다.

### 기존 레코드 처리

**이미 생성된 3건은 수정하지 않습니다.** append-only 원칙이 우선합니다. 수정 이후 레코드부터 새 형식이 적용되며, 형식이 갈리는 구간이 존재한다는 사실을 이 기록으로 남깁니다.

구현은 `check_commit_trailer.py`의 기존 트레일러 파싱 로직을 재사용합니다.

## D-015. 해소 레코드는 `main` push 성공 시에만 append

**상태**: 확정 | **일자**: 2026-09-13
**근거**: `TASK-003_DECISION_REQUEST_2026-09-13.md` D-R10

### 상황

동일한 수정 1건(커밋 `2f918c7`)에 대해 해소 레코드가 3개 생성되었습니다 — PR 브랜치 성공 2회(push 트리거, pull_request 트리거) + main 병합 후 push 트리거 1회.

### 결정 — 점검 의견 (b) 채택

```
guard 성공 + 트리거가 main push + HEAD 에 Failed-Run: 트레일러
→ 해소 레코드 append
```

**PR 단계의 성공은 해소가 아닙니다.** 이후 커밋이 추가되면 뒤집힐 수 있는 상태를 "해소됨"으로 기록하면 그 레코드가 거짓이 될 수 있습니다.

해소 레코드의 가치는 "고쳤다는 주장"이 아니라 **"고쳐진 것이 확정됐다"는 증거**입니다. main 병합이 그 확정 시점입니다.

**부수 효과**: 중복이 사라지면 미해소 잔존 레코드를 세는 것이 의미를 갖습니다. 한 수정에 3건이 붙으면 주간 보고의 "해소 확인률"이 왜곡됩니다.

### 17-a. 합성 세션 기준 경로 — 익명화본을 저장소에 커밋

오프셋 값과 원본 GPX 는 저장소에 넣지 않는다
```

저장소에 남는 것은 위치 정보가 아니라 형상뿐이며, 원본과 대조할 수단이 없으면 복원이 불가능합니다. 오프셋은 일회성 변환이므로 재사용할 일도 없어집니다.

```
스텁 엔진은 결정론적이기만 하면 된다
예: 입력 프레임 수를 세어 고정 규칙으로 출력을 생성
안내 로직을 구현하지 않는다 — Phase 1 범위다
```

PR-6의 목적은 **리플레이 경로가 존재하는 것**이지 엔진이 아닙니다.

### 17-c. 앱 빌드 잡 Phase 0 제외 — 점검 의견 승인

관리 지시서 §3.2의 `assembleDebug`/`testDebugUnitTest` 잡을 Phase 0에서 제외한 판단을 승인합니다.

`:app`이 빈 스켈레톤이면 이 잡은 실패할 일이 없습니다. **검사기가 무언가를 잡는지 확인할 수 없는 잡을 넣으면 항상 초록불인 체크가 하나 생깁니다.** 함정 목록의 "아무것도 안 잡는 negative-control"과 같은 성질입니다.

## D-018. 점검 범위에 산출물 실질 검토를 포함

**상태**: 확정 | **일자**: 2026-09-14

### 상황

AKB 조회가 구현 결함 4건을 짚어냈습니다.

```
toolchain 전 필드 빈 문자열 — 추출 로직 부재
failed_task 가 워크플로 이름("guard")으로 고정 — 잡 구분 없음
빈 로그 레코드(log:"")가 스키마를 통과해 정상 커밋됨
log_ref 가 존재하지 않는 logs/ 디렉터리를 가리킴
```

**전부 tnApp 점검 에이전트가 먼저 잡았어야 할 것들입니다.** 특히 빈 로그와 무효 `log_ref`는 레코드 파일을 한 번 열어보면 드러납니다.

### 원인 진단

점검이 실패한 것이 아니라, **점검 범위가 형식에 한정되어 있었습니다.**

```
검증한 것   PR 별 완료 정의 충족 여부
            명령이 실행되었는가, 종료 코드가 기대와 같은가
            증거가 원문으로 첨부되었는가

검증하지 않은 것
            산출물의 내용이 쓸 만한가
            선언한 필드에 실제 값이 들어 있는가
            참조가 실제로 가리키는 곳이 있는가
```

워크플로가 "정상 종료"하고 레코드가 "생성"되었으므로 형식 기준으로는 전부 통과입니다. **그러나 생성된 레코드는 절반이 비어 있었습니다.**

이는 D-003에서 다룬 문제의 변형입니다. 검사기가 아무것도 검사하지 않으면서 초록불을 내는 상황과 같은 구조이며, 이번에는 검사 대상이 검사기가 아니라 산출물이었습니다.

### 결정

**점검 에이전트의 검증 항목에 산출물 실질 검토를 추가합니다.**

```
기록 계열 산출물(레코드, 세션 로그, 스키마 인스턴스)이 생성되면
1. 실제 파일을 열어 내용을 확인한다
2. 선언된 모든 필드에 유효한 값이 있는지 본다
   빈 문자열 · null · 하드코딩 상수는 결함으로 간주한다
3. 참조 필드(경로, ID)가 실제로 가리키는 대상이 존재하는지 확인한다
4. 동일 필드가 복수 레코드에서 항상 같은 값이면 하드코딩을 의심한다
```

4번이 이번 사례의 핵심 탐지 조건입니다. `toolchain`과 `failed_task`가 3건 전부 동일했던 것이 신호였습니다.

**"생성되었다"는 완료 정의로 불충분합니다.** 앞으로 작업 지시서의 완료 정의에는 산출물 내용에 대한 조건을 포함시킵니다.

## D-019. `toolchain` 실제 추출

**상태**: 확정 | **일자**: 2026-09-14

## D-020. `failed_task`를 실패한 잡 이름으로 기록

**상태**: 확정 | **일자**: 2026-09-14
**근거**: AKB Q2

`"guard"`는 워크플로 이름이며 정보량이 거의 없습니다. `guard.yml`은 6개 잡으로 구성되어 있고, 그 여섯은 성격이 다릅니다.

```
purity / session-format / replay / commit-trailer   검사기 기각 이력
negative-control / replay-determinism               검사기 자체의 고장 신호
(Phase 2 이후) 빌드 태스크                            빌드 실패
```

**두 번째 줄이 특히 구분되어야 합니다.** `negative-control` 실패는 코드 결함이 아니라 **검사기가 위반을 더 이상 잡지 못하게 됐다**는 신호입니다. 이것이 코드 실패와 같은 값으로 기록되면 D-003에서 세운 감시 구조가 보이지 않게 됩니다.

XCHG-001 §2.3이 검사기 기각 이력을 별도 공급 항목으로 규정했으므로, 현 형태는 계약 미충족이기도 합니다.

복수 잡 동시 실패 시의 표기(단일 문자열 vs 배열)는 구현 재량으로 둡니다. 결정 후 점검 에이전트가 기록하십시오.

## D-021. 빈 로그 레코드를 커밋하지 않음

**상태**: 확정 | **일자**: 2026-09-14
**근거**: AKB Q3

### 결정

```
log_sha256 == e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  (빈 문자열의 SHA256)
→ 레코드를 커밋하지 않고 워크플로를 실패시킨다
```

### 근거 — AKB 편의가 아니라 tnApp 자신의 문제

이 항목은 AKB 소비 편의가 아니라 **tnApp의 감지 체계가 무력화되는 경로**입니다.

주간 보고에 "마지막 실패 레코드 기록 일시"를 둔 목적은 기록 체계가 멈춘 것을 감지하기 위해서였습니다(토큰 만료, 워크플로 고장). 그런데 **빈 레코드가 계속 커밋되면 그 지표가 계속 갱신됩니다.** 체계가 죽었는데 살아 있는 것으로 보입니다.

누락된 레코드는 API 목록과 대조하면 드러납니다. 반면 빈 레코드는 스키마를 통과해 정상 레코드로 계수됩니다. **"레코드 3건"이 실제로는 1건인 상태**가 만들어집니다.

### 구현 시 유의

**재귀 위험**: 실패 보존 워크플로 자신의 실패가 다시 자신을 호출하는 경로를 차단해야 합니다. 빈 로그로 워크플로를 실패시킬 때 이 경로를 함께 검토하십시오.

## D-023. `schema_version` 상향 및 형식 경계 명시

**상태**: 확정 | **일자**: 2026-09-14

D-014, D-015, D-019~D-022가 레코드 형식을 변경하므로 `schema_version`을 올립니다.

### 기존 레코드는 수정하지 않습니다

append-only 원칙이 우선합니다. 원본을 고치면 "그 시점에 무엇이 기록됐는가"가 훼손되며, 이는 tnApp 기록 체계의 근간입니다.

**따라서 형식이 갈리는 구간이 저장소에 영구히 남습니다.**

```
수정 이전   toolchain 빈 문자열, failed_task="guard", log_ref 무효,
           resolution run_id 중복, 해소 레코드 3중 생성, 일부 빈 로그
수정 이후   위 항목 전부 정상
경계        schema_version 으로 구분
```

이것은 결함이 아니라 append-only의 대가입니다. 소비 측은 `schema_version`으로 분기 처리합니다.

`schema_version`을 채택한 이유가 여기서 실증되었습니다 — 통지 의무 없이 소비 측이 변경을 자력 감지하는 경로입니다.

## D-024. D-015 트리거 조건 정정 — `HEAD`가 아니라 push 커밋 범위

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-015
**근거**: AKB `XCHG-006` §2.1

### 결함

D-015는 다음과 같이 규정했습니다.

```
guard 성공 + 트리거가 main push + HEAD 에 Failed-Run: 트레일러
→ 해소 레코드 append
```

**`HEAD`를 보는 부분이 오류입니다.** 병합 전략에 따라 트레일러가 HEAD에 없습니다.

```
merge commit   HEAD = "Merge pull request #N from ..."
               트레일러는 부모 커밋에 있고 HEAD 에는 없다

squash merge   기본 메시지가 PR 제목 + 본문에서 합성됨
               원 커밋의 트레일러가 유실될 수 있다

rebase merge   마지막 커밋에 트레일러가 없으면 찾지 못한다
```

D-006에서 merge commit과 squash를 **둘 다 허용**해 두었으므로, 이 취약점이 발동할 조건이 이미 갖춰져 있었습니다.

### 실패 양상이 더 나쁩니다

```
빈 레코드(D-021)   저장소에 보인다. 세면 드러난다
해소 0건           아무것도 남지 않는다. 워크플로는 정상 종료한다
```

같은 계열의 문제이며, **이쪽이 더 보이지 않습니다.** D-021을 결정하면서 바로 옆의 D-015에 같은 함정을 만들어 둔 셈입니다.

### 결정

```
guard 성공 + 트리거가 main push
→ push 이벤트의 커밋 범위 전체를 훑는다
   payload.commits[] 또는 before..after 범위
→ Failed-Run: 트레일러를 가진 커밋을 찾아 해소 레코드 append
```

병합 전략과 무관해집니다.

**D-015의 판단 자체는 유지됩니다.** PR 단계의 성공은 이후 커밋으로 뒤집힐 수 있으므로 main 병합 시점에만 기록한다는 근거는 그대로입니다. 바뀌는 것은 **어디서 트레일러를 찾는가**뿐입니다.

### 검증 요건 추가

수정 실증 시 **병합 전략별로 확인**하십시오. 한 가지 전략에서만 확인하면 나머지에서 0건이 되는 상태를 놓칩니다.

## D-025. `failed_jobs` — 배열로 고정, 필드명 변경

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-020
**근거**: AKB `XCHG-006` §2.2

### 결정

D-020에서 구현 재량으로 미뤘던 표기 방식을 총괄이 확정합니다.

```
필드명   failed_task  →  failed_jobs
형식     항상 배열. 1건일 때도 배열
예       "failed_jobs": ["purity"]
         "failed_jobs": ["purity", "replay"]
```

### 근거

**`guard`의 6개 잡은 병렬 실행입니다.** 한 run에서 둘 이상 실패하는 것은 비정상이 아니라 정상입니다. 단일 문자열이면 정보가 사라집니다.

**타입이 상황에 따라 바뀌는 것이 더 나쁩니다.** 1건일 때 문자열, 2건 이상일 때 배열이면 소비 측이 매번 분기해야 하고, 그 분기를 빠뜨리면 조용히 틀립니다.

필드명을 복수형으로 바꾸는 이유는 **이름이 타입을 드러내게** 하기 위해서입니다. `failed_task`라는 이름은 단수를 암시해 소비 측의 오해를 부릅니다. 어차피 `schema_version`이 올라가는 사이클이므로 지금이 바꿀 시점입니다.

## D-026. `toolchain` — 값의 출처를 레코드에 명시

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-019
**근거**: AKB `XCHG-006` §2.3

### 배경

D-019는 "CI 실행 시점에 실제 추출"이라고만 규정했습니다. 그러나 실제로는 두 종류가 섞입니다.

```
실행 산출값   java -version, gradlew --version 등의 출력
             그 버전으로 실제로 돌았다는 증거

파일 선언값   libs.versions.toml, gradle-wrapper.properties
             그 버전을 쓴다고 적혀 있었다는 기록
```

AGP는 실행값을 얻기 어려워 선언값이 될 것이고, 그 자체는 문제가 아닙니다. **섞여서 구분이 안 되는 것이 문제입니다.** 소비 측이 판정에 쓸 때 두 값의 증거 강도가 다릅니다.

### 결정

**값 자체에 출처를 붙입니다.**

```json
"toolchain": {
  "gradle": { "value": "8.x", "source": "runtime" },
  "jdk":    { "value": "17.x", "source": "runtime" },
  "agp":    { "value": "8.x", "source": "declared" },
  "kotlin": { "value": "2.x", "source": "declared" },
  "ndk":    { "value": "",    "source": "unavailable" }
}
```

```
source 값
  runtime      실행 산출값
  declared     파일 선언값
  unavailable  둘 다 얻지 못함 (값은 빈 문자열)
```

### 구현 방식을 이렇게 정한 이유

```
필드를 나누는 방식        소비 측이 두 곳을 봐야 한다
스키마 문서에만 적는 방식   레코드만 보는 쪽이 놓친다
```

**레코드가 자기 증거 강도를 스스로 밝히는 형태**가 낫습니다. 문서를 참조하지 않고도 판정이 가능합니다.

`unavailable`을 명시적 값으로 둔 이유는 D-018 때문입니다. 빈 문자열만 있으면 "추출 실패"인지 "해당 없음"인지 구분되지 않고, 그것이 이번 사이클에서 고치는 결함의 원인이었습니다.

### 근거 — AKB S0-R 구조적 발견 6번

AKB는 로그 텍스트에서 추측한 값으로 로그 텍스트를 판정했고, 그것이 S0-R 후반부 전체를 관통한 결함이었습니다. **선언값과 실행값을 섞으면 tnApp이 같은 함정에 들어갑니다.**

`toolchain`을 채우기로 한 애초의 근거가 "tnApp은 자기 CI가 무엇을 돌렸는지 이미 안다"는 독립성이었습니다. 출처를 구분하지 않으면 그 독립성이 절반만 성립합니다.

## D-027. `trigger_event` 필드 추가 및 해소 확인률 산정 기준

**상태**: 확정 | **일자**: 2026-09-14
**근거**: `TASK-005_INSPECTION_REVIEW_2` §3

### 상황

동일 위반 커밋이 push 이벤트와 pull_request 이벤트 양쪽에서 각각 `guard`를 트리거해, 서로 다른 `run_id`로 두 번 실패 기록됩니다.

```
34785171158  merge 전략, push 트리거       ← Failed-Run: 트레일러가 참조
34785248674  같은 커밋, pull_request 트리거  ← 영구히 해소가 붙지 않음
34785360381  squash 전략, push 트리거      ← Failed-Run: 트레일러가 참조
34785405829  같은 커밋, pull_request 트리거  ← 영구히 해소가 붙지 않음
```

`record-failure` 잡이 `conclusion == 'failure'`만 조건으로 하고 이벤트 종류를 가리지 않으므로 **설계상 정상적인 부산물입니다. 결함이 아닙니다.**

점검 에이전트의 판단과 귀결 분석(해소 확인률 해석 시 감안 필요)은 정확합니다. **다만 "기록만" 하는 처리로는 불충분합니다.**

### 왜 조치가 필요한가

```
해소 확인률 = 해소된 실패 / 전체 실패
```

이 지표는 원래 **"고쳤다고 커밋했으나 실제로는 통과하지 못한 사례"**를 잡기 위한 신호입니다. 거기에 **애초에 해소가 붙을 수 없는 레코드**가 섞이면 신호가 묻힙니다.

지표가 구조적으로 100%에 도달할 수 없게 되면, 미달을 보고도 "원래 그렇다"로 넘기게 됩니다. 그 순간 지표가 죽습니다.

AKB 측 영향도 있습니다. 실패 레코드 수가 실제 실패 사건보다 많고 그 배수가 트리거 구성에 따라 변합니다. **D-015에서 해소 레코드 3중 생성으로 이미 한 번 겪은 문제와 같은 계열입니다.** 알리지 않으면 AKB가 또 부풀려진 값을 집계합니다.

### 결정

```
레코드에 trigger_event 필드를 추가한다
  값: push / pull_request / workflow_dispatch / 기타 실제 이벤트명

주간 보고의 해소 확인률은 trigger_event == "push" 인 레코드만 분모로 한다
pull_request 트리거 레코드는 별도 집계한다
```

`schema_version`을 다시 올리게 되나 감수합니다. **지금 넣지 않으면 AKB 재조회 시 같은 문의가 다시 옵니다.**

### 처리 시점 — 이번 사이클에 묶지 않습니다

**G0 완료 판정은 이미 났고, 여기서 되돌리면 판정의 의미가 흐려집니다.**

Phase 1 착수와 병행해 별도 사이클로 처리하십시오. G0 재판정 대상이 아닙니다.

### 보고 규율 보완

점검 에이전트 §8의 "다음 사이클 시 자연스럽게 전달" 방침을 승인하되, 다음 문장을 구현 지시에 포함시킵니다.

```
이번에 생성된 산출물 전체 목록을 먼저 조회하고,
보고에 언급하지 않은 것이 있으면 그 사유를 적는다
```

언급 여부를 구현 에이전트 재량으로 두면 같은 누락이 반복됩니다.

## D-028. `engine_config` 선언-시행 일치 검증을 Phase 1 필수 산출물로

**상태**: 확정 | **일자**: 2026-09-14
**근거**: AKB `XCHG-006` §5 (`TRAILNAV_DECISIONS_4` 이월 항목)

### 배경

AKB S0-R 사례입니다.

```
screening 규칙 YAML v2 를 선언하고 declared_rule_sha256 도 일치했으나
실행 코드는 정적 v1 딕셔너리를 쓰고 있었다
형식 검사는 전부 통과했고, 측정 한 회차가 통째로 무효가 됐다
```

**tnApp에 같은 구조가 성립합니다.** 세션 매니페스트의 `engine_config` 해시가 일치해도, 엔진이 그 config를 실제로 읽고 있는지는 별개 문제입니다. 코드 상수가 config를 덮어써도 해시는 일치합니다.

### 결정

**Phase 1 산출물에 config 반응성 검증을 포함합니다. 선택이 아닙니다.**

```
검증 방식
  동일 세션에 서로 다른 config 를 주입해 출력이 실제로 달라지는지 확인
  예: guide.offRoute.enterDist 를 25m → 100m 로 변경
      같은 세션에서 이탈 판정이 사라져야 한다
      같은 판단이 나오면 그 파라미터는 읽히지 않고 있다

대상
  로드맵 §9 "설정 노출 O" 로 표시된 전 파라미터

형태
  CI 잡으로 구현한다. 반증 테스트와 같은 원리다
  잡 이름은 구현 재량 (예: config-sensitivity)
```

`purity` 검사가 "엔진이 외부 상태를 읽지 않는가"를 보는 것이라면, 이 검증은 **"엔진이 주어진 config를 실제로 읽는가"**를 봅니다. 두 방향이 합쳐져야 순수 함수 규약이 실효를 갖습니다.

## D-029. `config-sensitivity` 대상 파라미터의 누락 방지

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-028
**근거**: `TASK-007` §7.1 질의

### 결정

```
config-sensitivity 잡은 GuideConfig 의 필드를 열거해
검증 대상 목록에 없는 필드가 있으면 실패한다

## D-030. golden 세션 재생성 절차 및 `replay` 잡의 역할 명시

**상태**: 확정 | **일자**: 2026-09-14
**근거**: `TASK-007` §3 PR-3

### 문제

초안은 스텁 엔진 교체 후 "golden replay가 통과하는지 확인하고, 재생성이 필요하면 진행하되 사유를 쓰라"로 규정했습니다.

**이것은 관리 지시서 §4(3)이 경고한 사고의 재현 경로입니다.**

```
스텁을 실제 엔진으로 교체하면 guide 출력은 확정적으로 달라진다
→ golden replay 는 반드시 깨진다
→ 그 시점에 golden 을 재생성하면
   "엔진이 무엇을 출력하든 그것이 정답" 이 된다
```

검사 하네스가 자기 입력을 매칭하는 것과 같은 구조입니다. 더구나 **PR-3 시점에는 오탐 0이 아직 실증되지 않았습니다.** 검증되지 않은 엔진의 출력을 정답으로 굳히게 됩니다.

### 결정

**1. `replay` 잡의 역할을 문서에 명시한다**

```
replay        회귀 탐지용이다. 정확성 검증이 아니다
              "직전과 같은 출력이 나오는가" 만 본다
정확성 검증    PR-5 의 오탐 / 미탐 판정이 담당한다
```

이 구분이 없으면 replay 초록불을 정확성의 증거로 오독하게 됩니다.

**2. golden 재생성을 2단계로 나눈다**

```
PR-3   임시 재생성 (replay 잡 통과용)
       커밋 메시지와 세션 매니페스트에 "미검증 엔진 출력" 임을 남긴다

PR-5   오탐 0 · 미탐 0 실증 후 최종 재생성
       이것을 기준 golden 으로 고정한다
```

**3. 재생성된 golden 세션 매니페스트에 `code_hash`를 반드시 기록한다**

로깅 가이드에 이미 정의된 필드입니다. 지금 쓰지 않으면 나중에 "이 golden이 어느 엔진 버전의 출력인가"를 추적할 수 없습니다.

## D-032. 미탐 판정이 성립하는 세션 길이 요건

**상태**: 확정 | **일자**: 2026-09-14

```

시속 3km   약 230초

### 결정

```
조합 A · C 의 이탈 구간은
수직거리 50m 도달에 필요한 진행 길이 이상으로 구성한다
  15° 이탈 기준 최소 약 200m
  30° 이탈 기준 최소 약 100m
```

**작업 지시서의 함정 목록에 이 항목을 포함하십시오.**

각 조합 세션의 이탈 구간 길이와 도달 수직거리를 보고에 명시하게 하십시오. "미탐 0"만으로는 판정이 유효한지 알 수 없습니다.

## D-033. 엔진 반증 픽스처 — 검증 스택 전체에 대한 반증 테스트

**상태**: 확정 | **일자**: 2026-09-15
**근거**: `TASK-007` 1차 반려 (재구현체 검증)

### 무엇이 일어났는가

Phase 1 최초 구현 보고에서, **검증 도구 전체가 컴파일된 Kotlin 엔진을 호출하지 않고 Python으로 로직을 재구현해 그 재구현체를 테스트하고 있었습니다.** `guard.yml`에는 Kotlin 빌드 스텝 자체가 없었습니다.

```
purity                 통과   엔진을 보지 않으므로 당연히 통과
replay                 통과   재구현체끼리 비교하므로 항상 일치
replay-determinism     통과   같은 Python 이 두 번 같은 값을 냄
config-sensitivity     통과   재구현체가 config 를 읽으므로 반응함
phase1-accuracy        통과   재구현체가 오탐 0 을 냄
core-guide-build       부재   잡 자체가 없었음
```

**여섯 개 잡이 전부 초록불인 상태에서 실제 엔진은 단 한 줄도 실행되지 않았습니다.**

### 이것의 심각성

AKB가 공유한 S0-R screening 사례(선언된 규칙 해시는 일치했으나 실행 코드는 정적 구버전)와 같은 계열이지만 **더 심한 형태입니다.** 그쪽은 선언과 실행이 갈린 것이고, 이쪽은 **검증 대상이 아예 존재하지 않았습니다.**

그리고 **총괄이 설계한 어떤 장치도 이것을 잡지 못했습니다.** D-028(config 반응성 검증)은 "엔진이 config를 실제로 읽는가"를 보도록 만든 장치인데, 재구현체가 config를 읽으므로 그대로 통과했습니다.

D-003에서 "판정 주체를 기계로 옮긴다"고 했으나 이 유형은 기계가 잡지 못했고, 사람이 소스를 읽어 잡았습니다.

### 결정

**`negative-control`의 적용 범위를 엔진 소비 잡까지 확장합니다.**

```
Engine.kt 에 고의 결함을 주입한 픽스처를 둔다
  예: enterDwell 을 무시하고 즉시 off-route 전환
      config 값을 코드 상수로 덮어쓰기

→ phase1-accuracy / replay / config-sensitivity / core-guide-build
  전부 빨간불이 되어야 한다
→ 하나라도 초록불이면 그 잡은 엔진을 실제로 실행하지 않고 있다
```

### 왜 이것이 작동하는가

재구현체를 테스트하는 잡은 **엔진에 결함을 넣어도 통과합니다.** 그것이 탐지 신호입니다. 1차 보고 시점에 이 픽스처가 있었으면 자동으로 걸렸습니다.

기존 `negative-control`이 검사기(purity, session-format)의 고장을 잡는 장치라면, 이것은 **검증 스택이 대상을 실제로 건드리는지**를 잡는 장치입니다.

```
구현 형태   negative-control 잡 확장 또는 별도 잡 — 구현 재량
픽스처      Kotlin 소스이므로 컴파일 대상 제외 처리 필요
            기존 testdata/violations/ 관례를 따를 것
처리 시점   Phase 2 사이클
```

## D-034. D-027(`trigger_event`)을 Phase 2 사이클에 병합

Phase 2 완료 단계의 기기 테스트에서 UI 디자인 품질이 사용성을 떨어뜨리는 것이 확인되었습니다. 점검 에이전트 확인 결과 **로드맵에 디자인 관련 사항이 전혀 없다**는 보고가 있었고, 사실입니다.

그러나 이 앱은 **산에서 장갑 낀 손으로 한 손 조작하는 앱**입니다. 화면 가독성과 터치 타겟은 안내 정확도만큼 실사용을 좌우합니다. 오탐 0을 달성해도 경로를 고를 수 없으면 쓸 수 없습니다.

## D-036. Phase 2.5 신설 — UI 정비

**상태**: 확정 | **일자**: 2026-09-16

### 왜 지금 즉시 착수하지 않는가

```

Phase 2를 먼저 닫고 착수합니다.

### 완료 판정

**UI 품질은 CI로 판정할 수 없습니다.** 현장 체크리스트로 대체하며, G2-a 동네 경로 테스트에 끼워 수행합니다.

**다만 확인은 필요하며, 지금 즉시 가능합니다.**

```
UI 가 서비스 상태를 올바르게 다시 읽어오는가
세션 로그(loc / guide)에 끊김이 없는가
TTS 발화가 중단되거나 중복되지 않는가
```

**Phase 2.5가 아니라 Phase 2 기기 테스트에서 처리하십시오.** 안내를 켠 상태로 접었다 펴고 세션 로그를 확인하면 됩니다. 이미 만들어진 기능의 검증이므로 미룰 이유가 없습니다.

→ 하드코딩하면 한쪽에서 틀린 방향을 가리킨다

## D-039. 엔진 판단 시각화 — 경로 상대 좌표 리본

**상태**: 확정 | **일자**: 2026-09-16
**대상 Phase**: 2.5 (신규 기능 항목)

---

### 1. 관측된 문제

Phase 2 기기 테스트에서 **사용자가 경로 위에 있을 때 앱이 제공하는 정보가 부족하다**는 것이 확인되었습니다.

현재 구조상 안내는 이탈·종착 시에만 발생합니다. 정상 진행 중에는 아무 일도 일어나지 않으며, 이것이 설계 의도였습니다.

**그러나 사용자 경험상 침묵은 "정상"이 아니라 "모름"으로 읽힙니다.**

```
앱이 침묵한다
→ 맞게 가고 있는지 확신이 없다
→ 화면을 본다
→ 화면에도 확신을 주는 것이 없다
→ 계속 본다
```

이는 프로젝트 초기에 정의한 핵심 페인포인트와 정확히 일치합니다. **사용자의 고통은 "길을 모른다"가 아니라 "맞는지 확신이 없다"입니다.**

---

### 2. 지도를 넣지 않는다

소유자 판단이며 총괄도 동의합니다.

```
지도 도입 시 따라오는 것
  타일 캐시 · 오프라인 다운로드 관리 · 저장 공간
  렌더링 배터리 소모
  위치 정보 노출면 확대
얻는 것
  "내가 어디 있나" — 이미 음성이 답하고 있는 정보
```

비용 대비 효용이 맞지 않습니다. **범위 밖 유지**를 재확인합니다.

---

### 3. UI 제1원칙과의 충돌 검토

D-037이 수립한 원칙은 다음과 같습니다.

```
화면은 보조 채널이다
안내 중 화면은 정보를 최소한만 띄운다
```

**이 결정은 표면상 원칙에 반합니다. 그러므로 명시적으로 검토합니다.**

원칙의 목적은 **"화면을 덜 보게 하는 것"**이지 "정보를 적게 주는 것"이 아닙니다.

현 상태는 정보 부족이 **오히려 화면 응시 시간을 늘리고 있습니다.** 한 번 봐서 즉시 안심되면 보는 횟수가 줄어듭니다.

```
판정   3초 판독 기준(D-036 체크리스트)을 충족하는 한 원칙 위반이 아니다
       충족하지 못하면 이 기능은 원칙 위반이며 축소 대상이다
```

**3초 기준이 이 기능의 존속 조건입니다.**

### 4. 사양 — 경로 상대 좌표 리본

엔진이 이미 산출하는 값만 사용합니다. **새로 계산할 것이 없습니다.**

```
경로를 직선 리본으로 펼쳐 세로 표시
  위쪽이 진행 방향, 아래가 지나온 구간

리본 좌우에 임계 밴드
  ±exitDist  (15m)  복귀선 — 연한 색
  ±enterDist (25m)  이탈선 — 진한 색

사용자 점을 수직거리 d 만큼 좌우로 오프셋
  리본 중앙 = 정상. 한눈에 판독된다

점 주위에 GPS 정확도 반경을 반투명 원으로 표시

진행 방향 표시 (정방향 / 역방향 / 정체)
종착지까지 남은 거리
```

밴드 폭은 **config 값을 읽어 그립니다.** 하드코딩 금지 — D-028의 config 반응성 요구가 UI에도 적용됩니다.

### 이것이 지도보다 나은 이유

```
지도    "내가 어디 있나" 를 보여준다
리본    "앱이 나를 어떻게 보고 있나" 를 보여준다
```

후자가 신뢰의 근거입니다. 사용자가 판단 근거를 직접 확인할 수 있으면 침묵이 "모름"이 아니라 "정상"으로 읽힙니다.

### 5. 필수 요건 — GPS 정확도 표현

**이것은 선택 항목이 아닙니다.**

`d` 값만 그리면 accuracy가 나쁠 때 점이 심하게 튑니다.

```
오차 반경 없음   사용자는 "앱이 헤맨다" 로 읽는다 → 신뢰 하락
오차 반경 있음   "지금 신호가 나쁘다" 로 읽는다   → 상황 이해
```

**같은 흔들림인데 해석이 정반대가 됩니다.** 정확도 표현이 없으면 이 기능은 신뢰를 높이는 대신 떨어뜨립니다.

조정은 G2-b(실제 산행) 실측 이후에만, 총괄 결정으로
```

## D-040. 로그 시간 규약 — 옵션 A 채택, 조건 3건

**상태**: 확정 | **일자**: 2026-09-20
**근거**: 결정 요청 §결정 1

### 결정

```
t     사건 발생 시각. 스트림별 단조 증가
seq   기록 순서. 전체에서 엄격히 증가
```

둘은 다른 시계이며, 이것이 정직한 규약입니다. `validate_session.py`는 스트림별 단조성을 검사하고, 전체 순서는 `seq`로 판정합니다.

**옵션 B를 기각한 이유**: 로거가 파일 순서를 꾸미게 되고, `route.orientation`의 `t` 정의까지 바꿔야 하며, **이미 수거한 실산 로그와 호환이 깨집니다.** 그 로그는 다시 얻으려면 산에 한 번 더 가야 합니다.

### 조건 1 — 인덱스 짝짓기에 불변식 검사를 붙일 것

k번째 loc ↔ k번째 guide 짝짓기는 **loc과 guide가 1:1일 때만** 성립합니다. 현재 759/759, 6075/6075로 성립하지만 **이는 암묵 가정입니다.**

한 프레임이라도 누락되면 짝짓기가 통째로 밀리고, **replay는 조용히 틀린 비교를 통과시킵니다.** 실패보다 나쁩니다.

```
필수   replay 는 loc 수와 guide 수가 다르면 즉시 실패한다
권장   guide 이벤트에 원본 loc 의 seq 를 기록한다 (src_seq)
```

`src_seq`를 권장합니다. 위치 기반 암묵 규칙을 명시 참조로 바꾸는 것이고, 어차피 필드를 추가하는 사이클입니다.

### 조건 2 — `code_hash`를 고치되 필드를 늘리지 말 것

git SHA 필드를 따로 추가하고 `code_hash`에 버전 문자열 해시를 남겨두면 **거짓말하는 필드가 그대로 남습니다.** D-022에서 `log_ref`를 제거한 것과 같은 판단입니다.

```
code_hash 값 자체를 git commit SHA 로 교체
로컬·미커밋 빌드는 -dirty 표기
```

### 조건 3 — 비식별 픽스처는 전체가 아니라 최소 구간으로

**소유자 승인 완료 (2026-09-20).**

```
대상   실산 세션 중 10분 내외 구간
       시작 구간 버퍼 재생(t 역행 발생 지점)
       프레임 간격 1초 미만 구간
       이탈 진입 ~ 복귀 1회
방식   좌표 평행이동 + 시각 이동 (D-017-a 와 동일 방식)
금지   오프셋 값과 원본 로그를 저장소에 넣지 않는다
```

전체 세션(5.3MB)을 넣을 이유가 없습니다. 필요한 것은 **형상**이며, 구간을 줄이면 개인 위치 노출면과 CI 실행 시간이 동시에 줄어듭니다.

### 이 조치가 필요한 근본 이유

**CI는 실제 앱이 만든 로그를 한 번도 검증한 적이 없습니다.** golden/synth는 전부 우리가 만든 데이터입니다. 이번 두 결함이 정확히 그 틈에서 나왔습니다.

```
t 역행        실제 로그에만 있는 형상 → validate_session.py FAIL
1초 미만 간격  실제 31%, 픽스처는 초 단위 정수 → 엔진 결함 미검출
```

산에 다녀와야만 발견되는 상태였습니다. D-040은 이 틈을 닫습니다.

## D-041. G2 완료 기준 — 보충 시험 채택, 배터리 기준 변경

**상태**: 확정 | **일자**: 2026-09-20
**근거**: 결정 요청 §결정 2, ADDENDUM 2·3

### 결정 — 옵션 1 (기준 유지 + 보충 시험)

```
(a) 3시간 서비스 생존   경로 위 보행 불요. 일상 구동으로 충족
(b) 도착 판정 실측      짧은 경로로 종점까지 1회
(c) 정방향 시작 판정    (b) 와 동시 수행 가능
```

옵션 2(3시간 기준 완화)를 기각합니다. 제조사 강제 종료가 1시간 이후에 발생하는 경우를 검증하지 못한 채 남습니다.

### 배터리 기준 변경 — 순소모율 폐기, 총소모로 전환

baseline은 **미측정으로 확정**되었습니다(ADDENDUM 3). 순소모율은 산출 불가입니다.

**baseline 1시간 측정을 지시하지 않습니다.** 순소모율을 게이트에서 빼는 이상 별도 2시간(끈 채 1시간 + 켠 채 1시간)을 쓸 이유가 없고, **총소모는 3시간 생존 시험에서 자동으로 함께 측정됩니다.**

```
변경 전   배터리 순소모율 (baseline 필요)
변경 후   3시간 구동 총소모 35%p 이하
측정      앱 로그의 service.started ~ service.stopped 구간
```

### 총소모율 수치에 대한 정정

총괄이 결정 요청 답변 시 "8.4 %/h, 3시간 환산 25%p, 병목 아님"이라고 판단했으나 **단정할 수 없습니다.**

```
앱 로그     16%p / 113.9분 = 8.4 %/h   → 3시간 25%p
사용자 기록  20%p / 약 110분 = 10.9 %/h → 3시간 33%p
```

두 값이 30% 차이 납니다. 후자면 35%p 기준에 거의 붙습니다. **여유가 있다고 보지 않습니다.**

측정 기준을 앱 로그 구간으로 통일합니다. 사용자 기록은 앱 구동 전후(설정·화면 켬)가 섞여 비교할 수 없습니다.

### 앱 단위 배터리 설정 — 현재 값 유지

ADDENDUM 2로 **"최적화"(예외 아님)** 상태에서 101.3분 무중단이 확인되었습니다.

```
3시간 시험 중 앱 배터리 설정을 변경하지 않는다
변경하면 101분 결과와 비교가 불가능해진다
```

예외를 켜고 살아남는 것은 약한 증거입니다. 현재 값이 실제 기본값이며, 거기서 종료가 발생하면 그것이 D-R4 대응 범위를 정할 근거가 됩니다. **위험을 겨냥하지 않는 시험은 통과해도 의미가 없습니다.**

## D-042. 장기 이탈 시 음성 정책 — (c) 채택, (b) 기각

**상태**: 확정 | **일자**: 2026-09-20
**근거**: 결정 요청 §결정 3

### 엔진 변경 승인

`elapsedSeconds()`의 ms/초 휴리스틱 제거를 승인합니다. **파라미터 조정이 아니라 결함 수정이며 D-011과 충돌하지 않습니다.** TASK-019 선례와 같습니다.

```

`SensorFrame.timestamp`의 단위(epoch ms)를 KDoc으로 명문화하십시오.

### 더 중요한 것 — CI가 못 잡은 이유

D-033의 `dwell-bypass` needle이 존재했는데도 **자연 발생 버전이 통과했습니다.**

```
needle 은 있었지만 그 needle 을 찌를 입력이 없었다
```

원인은 픽스처의 프레임 간격이 실제와 다르다는 것입니다. 실산은 31%가 1초 미만인데 단위 테스트는 `5L`, `10L` 같은 초 단위 정수를 씁니다.

**따라서 다음 두 가지를 TASK-021에 포함합니다.**

```
1. 합성 세션 생성기가 실제 프레임 간격 분포를 반영할 것
   1초 미만 간격을 포함한다. D-016 · D-032 의 연장
2. 테스트·합성 데이터·replay 의 시각 단위를 ms 로 정합
```

### 일반 규칙 — 테스트 편의를 위한 프로덕션 분기 금지

**이 결함의 진짜 원인은 여기 있습니다.**

"작은 테스트는 초 단위를 쓰니까"라는 이유로 프로덕션 함수에 휴리스틱이 들어갔고, 그것이 실기기에서 **모든 대기시간 조건을 무력화**했습니다.

```
프로덕션 코드에 테스트 편의를 위한 분기를 두지 않는다
테스트가 프로덕션에 맞춘다. 그 반대가 아니다
```

이 규칙은 엔진에 한정하지 않습니다. 앞으로 유사한 분기가 발견되면 결함으로 취급합니다.

**Phase 3의 꺾임 예고는 대기시간 로직 위에 올라간다.** 현 상태로 얹으면 결함이 그대로 전파된다.

```

실산 로그에서 이탈 안내 47건 중 12건이 같은 경로로 중복됐다. 예고·확인은 발화 빈도가 더 높아 증상이 더 심해진다.

**더 중요한 것은 검증 불가 상태가 된다는 점이다.** 예고가 중복될 때 그것이 새 기능의 결함인지 기존 결함의 전파인지 구분할 수 없다. Phase 1에서 "엔진 문제인가 기기 문제인가 섞이면 원인 분리가 안 된다"고 판단한 것과 같은 구조다.

`validate_session.py`가 실산 로그에 대해 FAIL하는 상태에서 스키마를 동결할 수 없다. Phase 3은 새 안내 종류(`TurnAhead`, `TurnNow`, 온디맨드 `Status`)를 `guide` 스트림에 추가하므로, **기록 기반이 굳지 않은 상태에서 새 이벤트를 얹으면 나중에 전부 재검토해야 한다.**

D-040을 그대로 구현한 `validate_session.py`를 2026-09-20 실산 세션에 실행하면 **두 세션 모두 FAIL**한다(세션 1: 30건, 세션 2: 23건, 전부 `envelope`의 `t` 역행).

```
envelope 스트림이 두 종류를 함께 담는다
  event_stream=loc     수신 시각
  event_stream=guide   시작 구간 버퍼 재생 프레임의 (더 오래된) 시각
각 종류는 단조 증가다. 섞이면서 역행이 나타난다
```

`(stream, event_stream)` 단위로 검사하면 **두 세션 모두 역행 0건**이다.

### 결정 — A안 채택

```
"스트림" = stream
단, envelope 는 (stream, event_stream) 단위로 검사한다
```

`envelope`는 하나의 스트림이 아니라 **두 스트림의 합류 지점**이다. 따라서 이 단위가 규약의 본래 의도에 맞는다.

앱 매니페스트가 이미 선언한 `"t_order":"per-stream"`은 이 해석과 함께 **그대로 유지한다.** 서술 정정은 불필요하다.

### B·C안을 기각한 이유

```
B  envelope 를 t 검사에서 제외
   → 검증 범위를 포기한다. envelope 시각 오류를 영영 못 잡는다

C  로거가 envelope.loc / envelope.guide 로 분리 기록
   → 스키마 변경. 이미 수거한 실산 로그와 비호환
   → D-040 에서 옵션 B(로거 변경)를 기각한 근거에 그대로 걸린다
```

### 이것은 D-040의 오류가 아니다

규약 자체("`t`는 사건 발생 시각, 스트림별 단조")는 맞았고, **"스트림"의 단위가 불명확했을 뿐이다.** D-045는 정정이 아니라 해석 확정이다.

다만 그 불명확성의 원인은 총괄 측에 있다. 결정 요청서(`G2-b_DECISION_REQUEST`)가 "`loc`·`guide` 각각은 단조"라고만 기술하고 `envelope` 내부 교차를 빠뜨렸으며, D-040은 그 서술을 근거로 작성되었다. **구현은 결정서를 충실히 따랐다.**

점검 에이전트가 이 누락을 자기 문서의 결함으로 명시해 보고한 것은 올바른 처리다.

### 진행

**재작업 지시서는 이 회신을 기다리지 않고 A안 전제로 발행한다.** 변경 범위가 검증기 한 곳이다.

## D-046. 비식별 스캐너를 반증 테스트로 구성할 것

**상태**: 확정 | **일자**: 2026-09-21
**근거**: `TASK-021_DECISION_REQUEST` 통보 2

### 배경 — 비식별 절차가 무력화될 뻔했다

병합된 `anonymize_fixture.py`는 `loc`의 `lat`/`lon`/`t`만 변환한다. 그러나 실산 로그의 `guide` 이벤트는 프레임마다 `inputs.lat`, `inputs.lon`, `inputs.timestamp`(epoch ms)를 담고 있다.

```
10분 창 기준 601건
loc 만 변환하고 커밋했다면
실좌표와 실시각이 퍼블릭 저장소에 그대로 올라간다
되돌릴 수 없다
```

**합성 세션에서는 드러나지 않았다.** 합성 데이터의 해당 필드가 좌표가 아니었기 때문이다.

D-040을 만든 이유 — **CI가 실제 앱 로그의 형상을 본 적이 없다** — 가 비식별 도구 자체에도 그대로 적용된 사례다.

### 결정

변환 대상 필드 열거, 잔존 좌표·epoch 스캐너, `route.gpx_hash` 재계산을 요구사항에 넣는 것을 승인한다. **여기에 다음을 추가한다.**

```
스캐너를 반증 테스트로 구성할 것
  변환 전 원본을 스캐너에 넣으면 반드시 탐지되어야 한다
  탐지되지 않으면 스캐너가 고장 난 것이다
```

### 근거

**스캐너가 아무것도 찾지 못한 것과, 스캐너가 작동하지 않은 것은 출력이 같다.**

이 프로젝트에서 같은 유형이 세 번 발생했다.

```
1차  검증 도구가 재구현체를 테스트 — 여섯 잡 전부 초록불 (D-033)
2차  미탐 판정 세션이 짧아 misses=0 이 자동으로 나옴 (D-032)
3차  dwell-bypass needle 은 있었으나 찌를 입력이 없었음 (D-043)
```

이번이 네 번째가 될 뻔했다. 비식별은 실패 시 되돌릴 수 없으므로 다른 어떤 검사보다 반증이 필요하다.

## D-047. 무효 서명 레코드 12건의 처리 — A안 채택 및 추출기 반증 요구

**상태**: 확정 | **일자**: 2026-09-21
**근거**: `TASK-023_DECISION_REQUEST` 결정 1

### 상황

소유자 문의로 실패 기록을 점검한 결과, **쌓이는 양은 정상이었다.**

```
2026-09-20 12:00Z 이후 guard 26회 중 실패 2회
기록 2건 + 해소 기록 1건이 정확히 대응
나머지 24회는 첫 시도에 성공
```

그러나 `records/`의 **12건 전부 `error_signature`가 동일**하다.

```
dependency-graph-continue-on-failure: true
```

Gradle 설치 액션이 입력을 echo하는 헤더 줄이며 실패 내용이 아니다. `tools/preserve_failure_record.py`의 `ERROR_LINE` 정규식이 그 줄에 오탐하고, Kotlin 컴파일 오류(`e: file:///…`)는 매치하지 못한다.

**2026-09-14 수정은 콜론을 요구했으나 그 줄에도 콜론이 있어 무효였다.** 고쳤다고 판단한 상태로 일주일이 지났다. 추출기를 검사하는 테스트가 없었다.

### 결정 — A안

```
기존 12건   불변. 수정하지 않는다
이후 생성분  failrec-2.0.1 (patch)로 구분. 필드는 늘리지 않는다
소비 측     2.0.0 의 서명을 무효로 보고 log 에서 재계산한다
안내        실패 기록 저장소 README 에 append
            "2.0.0 레코드의 error_signature 는 무효" — 원인과 기간 명시
            레코드가 아니라 안내문이다
```

### 이 수습이 가능한 이유 — 원문 보존 결정이 구했다

AKB가 `XCHG-002` Q3에서 `error_signature`를 정규화하지 말고 **원문을 보존하라**고 권고했고, tnApp이 이를 수용했다(`XCHG-003`).

```
log 원문이 레코드에 보존되어 있다
→ 서명이 틀려도 로그에서 재계산할 수 있다
→ 실제 로그에서 도출한 기준표로 12건이 7종으로 나뉨을 확인했다
```

**정규화를 했더라면 12건은 복구 불가였다.** 비가역 처리를 피한 결정이 1주일 뒤의 결함을 수습 가능하게 만들었다. 기록에 남길 가치가 있다.

### B·C·D를 기각한 이유

```
B  정정 레코드(corrections/) 신설
   → 새 레코드 종류 = 스키마 추가
   → "AKB 때문에 추가 구현 부담을 지지 않는다" 원칙과 충돌

C  기존 12건 재작성
   → 레코드 원본 불변 원칙 위반. 금지

D  구분 없이 이후만 올바르게 기록
   → 같은 schema_version 안에 의미가 다른 서명이 섞인다
   → 소비 측이 구분할 수 없다. D-026 의 정신에 어긋난다
```

### 추가 요구 — 추출기에 반증 테스트

**D-046과 같은 요구다.**

```
실제 로그 샘플에서 기대 서명을 뽑아 고정하고
추출기가 그 줄을 고르는지 검사할 것
사례는 실제 발생한 7종을 쓸 것
  Kotlin 컴파일 오류(e: file:///…), Gradle 태스크 실패, 테스트 실패 등
```

**추출기가 틀린 줄을 고르는 것과 올바른 줄을 고르는 것은 둘 다 "한 줄"을 내놓는다.** 출력 형태로는 구분되지 않는다. 2026-09-14 수정이 무효인 채 일주일을 버틴 이유가 정확히 이것이다.

### 진행

```

R0 지연은 게이트인 R1·R2·R3 를 막지 않는다 — 서로 다른 파일이다
```

## D-048. 주간 보고에 실패 레코드 표본 점검 추가

**상태**: 확정 | **일자**: 2026-09-21
**갱신 대상**: D-018

### 배경

D-018의 탐지 조건 4번은 다음과 같다.

```
동일 필드가 복수 레코드에서 항상 같은 값이면 하드코딩을 의심한다
```

이 조건은 **저장된 레코드 여러 건에 적용되지 않았다.** 이전 점검에서는 설계 확인에만 쓰였고, 이번에 처음 실제 레코드에 적용해 12건 전부 동일 서명임을 발견했다.

### 이것은 점검 에이전트만의 누락이 아니다

**총괄의 D-018 서술이 원인의 일부다.**

```
D-018 서술   "기록 계열 산출물이 생성되면 … 실제 파일을 열어 확인한다"
읽힌 방식    생성 시점의 1회 검토
빠진 것      이미 쌓인 레코드를 주기적으로 훑는 요구
```

D-018을 만든 계기 자체가 **AKB가 레코드 3건을 비교해 `toolchain` 하드코딩을 찾아낸 것**이었음에도, 그 방식(누적분 횡단 비교)이 정기 절차로 옮겨지지 않았다.

### 결정

```
주간 보고에 실패 레코드 표본 점검을 포함한다
  최근 N건에서 동일 값이 반복되는 필드를 확인한다
  N 은 점검 에이전트가 정한다 (전수일 필요 없다)
```

### 왜 숫자 지표로는 부족한가

기존 주간 보고 항목은 전부 정상이었다.

```
마지막 실패 레코드 기록 일시   정상
실패↔수정 쌍 연결률           정상
해소 확인률                   정상
```

**레코드 수도 해소율도 맞는데 내용이 전부 같았다.** 집계 지표는 내용의 공허함을 드러내지 못한다. 표본을 직접 열어보는 절차가 따로 있어야 한다.

## D-049. README 안내문 교체 및 실패 기록 저장소 수기 쓰기 금지

### 49-a. README 안내 절을 교정본으로 교체 — 안 1 채택

커밋 `e19bf27d`의 안내문 결함은 다음과 같다.

```
결정   안내 절을 교정본으로 교체한다 (별도 커밋)

**README는 레코드가 아니므로 불변 원칙의 대상이 아니다**(D-047). 틀린 안내를 남겨두는 것이 더 해롭다. D-047의 "append"는 안내문을 레코드처럼 다루라는 뜻이 아니었다.

안 2(정정 절 append)는 잘못된 안내와 정정이 함께 남아 소비 측이 혼동하고, 제어문자도 남는다. 기각한다.

### 49-b. 작성 경로가 드러낸 것 — D-010의 전제가 깨졌다

**깨진 문자의 패턴이 작성 경로를 가리킨다.**

```
PowerShell 에서 백틱은 이스케이프 문자다
  `f  → 폼피드
  `e  → ESC
마크다운 인라인 코드의 백틱이 PowerShell 문자열 안에서 해석되면
정확히 위 결함이 나온다
시각의 12시간제 현지 표기도 PowerShell Get-Date 기본 형식과 일치한다
```

**이 README는 워크플로가 아니라 Windows 머신에서 사람 계정 자격으로 직접 쓰였을 가능성이 높다.** 점검·구현 에이전트가 도는 그 머신이며, 거기에는 소유자 계정 전권이 붙어 있다(D-008).

             실질적 보호는 자격증명 범위다
실제         소유자 계정 인증이 붙은 머신이면 누구든 쓸 수 있다
```

**D-010의 "실질적 보호는 자격증명 범위"는 성립하지 않았다.** 토큰 범위를 좁혀도, 더 넓은 자격증명이 같은 머신에 있으면 의미가 없다. 총괄이 D-010 작성 시 D-008(소유자 계정 인증 부여)과의 관계를 검토하지 않았다.

`tnapp-failure-log`는 프라이빗이므로 브랜치 보호를 걸 수 없다(D-006). **막을 장치가 없으므로 탐지로 대체한다.**

### 4. 설계 시 유의 사항

**4.1 음성과 화면의 정합성 (D-039 §8)**

온디맨드 확인 음성과 리본 화면은 같은 정보를 다른 채널로 전달한다. **발화 항목과 표시 항목이 어긋나지 않도록 설계하고, 그 정합성을 검증 항목으로 둔다.** 어긋나면 사용자가 둘을 대조하게 되고 그 자체가 불신의 원인이 된다.

**4.2 꺾임 예고의 알려진 한계**

```
직진형 분기   GPX 상 방위각 변화가 0 → 예고가 원리적으로 불가능
경로 데이터   파일에 없는 갈림길이 실제로 존재한다 (G2-b ADDENDUM 1 §2, 10:32 건)
```

**둘 다 GPX만으로는 해결할 수 없다.** 구현에서 해결하려 들지 않는다. 테스트에서 이를 결함으로 오인 보고하지 않도록 지시서에 명시한다.

**4.3 새 파라미터는 D-029로 자동 포착된다**

꺾임 예고 거리(60m / 15m) 등 Phase 3에서 `GuideConfig`에 추가되는 필드는 `config-sensitivity`의 필드 열거에 자동으로 걸린다. 테스트를 쓰거나 명시적 제외 선언을 해야 병합된다. **지시서에서 별도로 상기시킬 필요가 없다.** 이것이 D-029를 만든 이유다.

**4.4 예상 결정 요청 지점**

```
D-R6  온디맨드 트리거 최종 선택 (미디어 버튼 vs 흔들기)
      — 둘 다 만들어 실사용 비교 후 결정
D-R7  꺾임 예고 오예고율이 높을 경우 탐지 각도(45°) 조정 여부
```

D-R7은 D-011이 적용된다. **동네 테스트(G2-a) 결과로 조정하지 않는다.**

### 5. G3 판정 선행 조건 (D-044 §6 재확인)

Phase 3 착수는 가능하나 **G3 판정은 다음이 모두 종료된 뒤에만 가능하다.**

```
G2 보충 시험 3건 — 3시간 생존 / 도착 판정 / 정방향 시작
배터리 총소모 35%p 이하 (D-041)
스키마 v1 동결
```

## D-052. D-049-c 탐지 전제의 정정 및 구현 채택

**상태**: 확정 | **일자**: 2026-09-21
**갱신 대상**: D-049-c
**근거**: `TASK-023_INSPECTION_REVIEW_2_v2` §3

### 1. 총괄 측 오류

D-049-c는 다음과 같이 기술했다.

```
탐지는 비용이 거의 없다
워크플로 커밋과 수기 커밋은 작성자 신원이 다르다
```

**사실이 아니다.** 실패 기록 저장소 커밋 조회 결과:

| 커밋 | 성격 | author / committer |
|---|---|---|
| `ffe692b9` | 워크플로 | `twenione` |
| `628121e4` | 워크플로 | `twenione` |
| `e19bf27d` | README, 수기 추정 | `twenione` |

`push_failure_record.py`가 Contents API의 `PUT`에 `author`·`committer`를 지정하지 않아 **토큰 소유자 신원이 그대로 쓰인다.** 작성자 신원으로는 둘을 구분할 수 없다.

**D-049-c를 그대로 시행했다면 탐지가 항상 "이상 없음"을 냈다.** 실패할 수 없는 검사를 총괄이 직접 설계한 셈이다.

**총괄이 확인하지 않고 단정했다.** D-047에서 건수를 요청서로부터 검증 없이 옮긴 것과 같은 유형이며, 이번에는 요청서 근거도 없이 추정을 사실로 적었다.

### 2. 결정 — 점검 에이전트의 4단계 조치를 채택한다

```
1. 워크플로가 쓰는 모든 커밋에
   고정된 워크플로 신원과 실행한 Actions run 의 링크(트레일러)를 남긴다
   → 신원 검사가 성립하고, 신원을 위조해도 run 존재 대조가 남는다

2. 로컬(Actions 밖)에서 실행되면 쓰기 스크립트가 거부한다
   → 사고성 수기 쓰기를 코드가 막는다

3. 주간 점검(D-048)의 커밋 검사를 읽기 전용 도구로 만든다
   → 사람이 기억하지 않아도 된다

4. 한계를 명시한다
   이 탐지는 사고(기본 신원으로 쓴 수기 커밋)를 잡는다
   위조는 막지 못한다. 브랜치 보호가 없는 한(D-006) 불가능하다
```

**2번이 가장 중요하다.** D-049-b에서 추정한 PowerShell 경로의 사고를 **탐지가 아니라 차단**한다.

이것은 새 결정이 아니라 **D-049-c의 전제를 성립시키는 구현**이다. TASK-024 (D)에 포함한다.

## D-053. 검사 장치의 공통 요건 — 반증 필수, 목록은 도구가 도출

**상태**: 확정 | **일자**: 2026-09-21
**근거**: `TASK-023_INSPECTION_REVIEW_2_v2` §2.1, §2.3~§2.5

### 1. 같은 결함이 다섯 번째로 나왔다

**실패할 수 없는 검사**가 이 프로젝트에서 반복된다.

```
1차  검증 도구가 재구현체를 테스트 — 여섯 잡 전부 초록불      D-033
2차  미탐 판정 세션이 짧아 misses=0 이 자동으로 나옴            D-032
3차  dwell-bypass needle 은 있었으나 찌를 입력이 없었음        D-043
4차  비식별 스캐너 (사전 차단)                                D-046
5차  형상 검사 recovery 가 guide 판정이 아닌 sys 이벤트를 봄    이번
     → 복귀 판정이 사라져도 이벤트만 있으면 통과
```

그리고 **사람이 관리하는 목록**에서 누락이 반복된다.

```
config-sensitivity 대상 파라미터 목록     D-029 로 해결
비식별 스캐너 위반 입력 목록             이번 — loc.t, 경로 GPX 좌표 누락
```

D-046, D-047에서 개별 검사마다 반증을 요구해 왔으나, **요구가 개별적이어서 새 검사가 생길 때마다 지시서가 빠뜨린다.** 형상 검사가 그 사례다(점검 에이전트 자인, §2.5).

### 2. 결정 — 일반 규칙으로 격상한다

**2.1 모든 검사 장치는 반증 입력을 갖는다**

```
새 검사를 추가할 때 그 검사가 실제로 FAIL 하는 입력을 함께 커밋한다
negative-control 이 그 입력에서 exit 1 을 확인한다
반증 입력이 없는 검사는 병합하지 않는다
```

**지시서가 매번 명시할 필요가 없다.** 이 결정이 기본값이다.

**2.2 검사 대상 목록은 사람이 아니라 도구가 도출한다**

D-029의 방식을 일반화한다.

```
검사 장치가 정의한 대상(필드 종류, 파라미터 등)을 도구가 열거하고
대응하는 반증 입력 또는 테스트가 없는 대상이 있으면 실패한다
```

적용 대상:

```
비식별 스캐너    스캐너가 정의한 필드 종류 11개
                각각에 위반 입력이 있는지 자동 대조 — loc.t, gpx 좌표 누락을 잡는다
형상 검사       7개 항목 각각에 반증 입력
                recovery 는 guide 판정을 근거로 하도록 수정
```

**2.3 검사는 판정의 근거가 되는 데이터를 직접 본다**

형상 검사 `recovery`가 guide 판정 대신 sys 이벤트의 존재를 본 것이 5차 사례의 원인이다. **부산물이 아니라 판정 자체를 검사한다.**

### 3. 실값 재발 방지 검사에 즉시 적용

`TASK-023_INSPECTION_REVIEW_2_v2` §2.1이 제안한 규칙 검사("2026년 범위의 epoch 숫자는 지정된 합성 창 밖에서 저장소 어디에도 있을 수 없다")는 D-053의 첫 적용 대상이다.

점검 에이전트는 현재 트리에서 **오탐 0건**을 확인했다. **그것은 절반이다.**

```
교체 전 5개 파일에 돌리면 5개 전부 탐지되어야 한다
```

**오탐 0건과 탐지 0건은 출력이 같다.** 교체 작업 전에 탐지를 확인하고, 교체 후 0건을 확인한다. 순서가 바뀌면 검사가 작동했는지 증명할 기회가 사라진다.

## D-054. 경로 이벤트 기반 동적 안내

**상태**: 확정 | **일자**: 2026-09-21
**대상 Phase**: 3
**갱신 대상**: 로드맵 §2.4(고도), D-044 미결 UX 후속("주기 안내 짧은 문구 · 신호음 선택지")

---

### 1. 관측과 판단

G2-b 실산 시험에서 경로 위 주기 안내("정상적으로 경로를 따라가는 중입니다")가 **안심감을 주었으나, 같은 문구의 반복이 지루했다**(소유자 체감).

**안심감의 원천은 문구가 아니라 신호다.**

```
신호   앱이 살아 있고, 나를 경로 위로 판단하고 있다
문구   그 신호를 전달하는 수단
```

같은 문구가 반복되면 청각이 이를 배경음으로 처리하고, **결국 신호 자체가 들리지 않게 된다.** 내용이 바뀌면 매번 주의를 끌면서 같은 신호를 전달하고, 부가 정보까지 얻는다.

**채택한다.**

---

### 2. 핵심 원칙 — 추가가 아니라 대체

**지루함을 고치려다 수다스러워지는 것이 가장 흔한 실패다.**

```
현재   주기마다 기본 문구
변경   주기 슬롯을 그때 가장 의미 있는 이벤트로 채운다
       마땅한 이벤트가 없으면 기본 문구로
```

**사용자가 정한 주기 설정이 전체 발화 빈도를 그대로 통제한다.** 발화량은 늘지 않고 내용만 바뀐다.

---

### 3. 이벤트 종류와 원천

| ID | 이벤트 | 원천 | 유형 |
|---|---|---|---|
| E1 | 거리 이정표 ("1킬로미터 지점입니다") | `s_proj` | 교차형 |
| E2 | 경과 시간 ("출발 2시간 경과") | `frame.timestamp` | 교차형 |
| E3 | 종착까지 남은 거리 ("종착지까지 1킬로미터") | 전체 길이 − `s_proj` | 교차형 |
| E4 | 오르막 · 내리막 예고 ("잠시 후 오르막입니다") | GPX `<ele>` 전방 프로파일 | 교차형 |
| E5 | 현재 고도 ("현재 고도 약 320미터") | GPX `<ele>` @ `s_proj` | 충전형 |
| E6 | 이름 지점 접근 ("잠시 후 형제산 정상입니다") | GPX `<wpt>` | 교차형 |
| E7 | 일몰까지 남은 시간 ("일몰까지 1시간") | 위치 · 날짜로 오프라인 계산 | 교차형 |

```
교차형   임계를 넘는 시점에 즉시 발화하고, 주기 타이머를 리셋한다
충전형   주기 슬롯이 비었을 때 채운다
```

**교차형을 슬롯까지 기다리게 하지 않는다.** "잠시 후 오르막"을 오르막 한가운데서 들으면 의미가 없다.

#### 3.1 E1 · E3은 GPS 누적 거리가 아니라 `s_proj` 기준

GPS 점 간 누적 거리는 노이즈로 부풀려진다. G2-b 세션처럼 **경로 밖(255m)에서 시작하면 기준점도 어긋난다.** 경로상 진행 위치를 쓴다.

**E3가 E1보다 가치가 크다.** 하산 페이스 판단에 직접 쓰인다.

#### 3.2 E7은 안전 기능이다

안전 사건 분류에 "일몰 후 미하산"이 이미 있다. E7은 다채로움을 넘어선 예방 장치다. 계산에 필요한 위치와 날짜는 프레임에서 얻으므로 **엔진 순수성을 해치지 않는다.**

---

### 4. 고도는 GPX에서만 읽는다 — 기기 측정 금지

**소유자 판단이며 총괄도 동의한다.**

```
GPS 고도     수평 오차보다 크고 10~30m 씩 튄다 → 사용 금지
기압계       상대값은 정확하나 절대값이 날씨에 따라 흐른다
             baro 는 실험 스트림(D-004) → 사용 금지
GPX <ele>    경로 파일 값. 위치 매칭(s_proj) 으로 읽는다 → 채택
```

"483미터"라고 자신 있게 말했는데 실제로 450미터면 D-R8의 원칙 — **틀린 정보를 자신 있게 주는 것은 주지 않는 것보다 나쁘다** — 에 걸린다.

#### 4.1 로드맵 §2.4와의 관계 — 번복이 아니다

로드맵 §2.4는 "고도는 사용하지 않는다"고 했다. **그 의미는 위치 매칭과 이탈 판정에 쓰지 않는다는 것이었으며, 이는 유지한다.**

```
판정 (매칭 · 이탈 · 종착)   고도 미사용 — 변경 없음
안내 콘텐츠 (E4 · E5)       GPX <ele> 사용 — 이번 결정으로 허용
```

#### 4.2 검증된 원천 — 불곡산 경로 GPX

`test01/수정_4.불곡산길.gpx`를 총괄이 직접 확인했다.

```
트랙 포인트   162개 전부 <ele> 포함
고도 범위     약 52m ~ 325m
포인트 간격   대략 50m
시각 정보     없음
```

**시각 정보가 없다 = 기록 궤적이 아니라 지도 위에 그린 경로이며, 고도는 지형 데이터에서 채운 값이다.** 값이 매끄럽게 이어지고 GPS 기록 특유의 튐이 없다. 오르막 · 내리막 예고에 그대로 쓸 수 있다.

파일 요약 정보: 오르막 256m(3.3km 구간), 내리막 356m(3.9km 구간), 평지 1.7km.

---

### 5. 웨이포인트(E6) — 안내용으로만 읽는다

불곡산 GPX에 이름 지점이 있다(형제산 정상 284m, 불곡산 스탬프 318m, 역 3곳).

**이름이 불리면 사용자가 주변 표지판과 대조할 수 있다.** 제안된 이벤트 중 "경로 위에 제대로 있다"는 확신을 가장 직접적으로 준다.

#### 5.1 경로 계산에는 섞지 않는다

```
엔진 경로 계산   trkpt(없으면 rtept) 만 사용 — 변경 없음
E6 안내          wpt 를 별도로 읽는다
```

TASK-023 검토(§2.2)에서 픽스처 경로에 `wpt`가 섞여 들어간 것을 결함으로 판정했다. **같은 원칙이다.**

#### 5.2 경로 근접 필터

역 3곳 등은 경로에서 떨어져 있을 수 있다. **경로에서 일정 거리 안에 있는 웨이포인트만 안내 대상으로 삼는다.**

---

### 6. 폴백 — 없는 정보를 만들어 말하지 않는다

불곡산 GPX는 조건이 좋다. **다른 GPX에는 고도나 웨이포인트가 없거나 노이즈가 클 수 있다.**

```
<ele> 없음            E4 · E5 생략. 나머지만
<ele> 있으나 노이즈    평활화 후 임계값 적용. 그래도 불안정하면 E4 · E5 생략
<wpt> 없음            E6 생략
```

**노이즈 판정 기준은 구현 재량이나, 판정 결과(고도 이벤트 사용 여부)를 세션 매니페스트에 기록한다.** 나중에 "왜 이 경로에서는 오르막 안내가 없었나"를 추적할 수 있어야 한다.

---

### 7. 우선순위와 억제

#### 7.1 우선순위

```
1  이탈 안내
2  꺾임 예고 (TurnAhead / TurnNow)
3  교차형 이벤트 (E1 · E2 · E3 · E4 · E6 · E7)
4  충전형 이벤트 (E5)
5  기본 문구
```

#### 7.2 억제 조건

```
이탈 중           전부 중단. 이탈 안내만
역방향 진행 중     이정표 · 예고 무의미 → E1 · E3 · E4 · E6 중단
신호 불량         accuracy 필터에 걸린 구간에서는 "경로 위" 계열 발화 자제
최소 간격         이벤트끼리도 간격을 둔다 (오르막 · 내리막이 잦은 구간)
동시 발생         우선순위가 높은 하나만 발화. 나머지는 버린다 (대기열에 쌓지 않는다)
```

**대기열에 쌓지 않는 것이 중요하다.** 쌓아두면 조건이 끝난 뒤 한꺼번에 쏟아지고, 이미 지나간 예고가 나온다.

---

### 8. 기록 — 이벤트 판단은 `guide` 스트림에

**앱이 알아서 말하면 리플레이에서 보이지 않는다.** 그러면 "왜 거기서 오르막이라고 했나"를 추적할 수 없다.

```
이벤트 판단     엔진이 내린다. Guidance 종류로 추가
기록           guide 스트림 (reason 포함)
문구 생성       앱. 구조화된 판단 → TTS 문장
```

엔진 순수성: GPX 고도와 웨이포인트는 **경로 로드 시점에 엔진 입력으로 주입**한다. 엔진이 파일을 읽지 않는다.

---

### 9. 파라미터

신규 파라미터는 전부 `GuideConfig`에 둔다. **D-029에 따라 `config-sensitivity`의 필드 열거가 자동으로 포착한다.**

초기값은 로드맵 v2 §9에 둔다. 구현 착수용이며 조정 대상이다.

#### 9.1 D-011과의 관계

```
이벤트 파라미터 (간격, 이정표 단위, 오르막 임계, 근접 거리)
  → 사용 경험 조정 대상. 동네 테스트(G2-a) 로 조정해도 된다
     GPS 오차에 판정이 좌우되는 값이 아니다

판정 파라미터 (이탈 임계 등)
  → D-011 그대로. 동네 테스트로 조정하지 않는다
```

---

### 10. 경계 — D-039 §7과의 관계

D-039 §7은 리본 시각화가 지도 대체재로 자라지 않도록 **"고도 프로파일" 추가를 총괄 결정 사항**으로 묶었다.

```
D-054 가 허용하는 것    GPX 고도를 음성 안내 콘텐츠로 사용
D-054 가 허용하지 않는 것 화면에 고도 프로파일 표시
                        → 여전히 D-039 §7 대상
```

**제1원칙(화면은 보조 채널)과 같은 방향이다.** 고도 정보는 귀로 듣는 것으로 충분하다.

---

### 11. 시험 데이터와 개인정보

**고도 프로파일은 모양과 결합하면 식별력이 크다.** 평행이동으로 위치를 숨겨도 고도 곡선이 산을 특정할 수 있다.

```
합성 세션      합성 고도 프로파일을 쓴다
실산 형상 픽스처 고도를 포함할 경우 합성 프로파일로 대체한다
               실산 고도를 그대로 넣지 않는다
```

D-053 §2.2에 따라 비식별 스캐너의 필드 열거 대상에 고도가 포함되는지 점검 에이전트가 확인한다.

---

### 12. Phase 3 편입 근거

```
E4 · E6 는 꺾임 예고와 같은 전방 내다보기 구조를 쓴다
Phase 3 는 어차피 음성 우선순위 체계(이탈 vs 예고 vs 온루트)를 만들어야 한다
```

**한 번에 설계하는 것이 따로 만드는 것보다 싸다.**

D-044의 미결 UX 후속 중 "주기 안내 짧은 문구"는 이 결정이 흡수한다. **"신호음 선택지"는 유지한다** — 최소 안내를 원하는 사용자를 위한 선택지로서 여전히 유효하다.

### 13. G3 판정 추가 항목

```
□ 주기 슬롯이 이벤트로 대체되며, 발화 빈도가 주기 설정을 넘지 않는가
□ 이탈 중 이벤트 발화가 0 건인가
□ 교차형 이벤트가 해당 지점에서 발화했는가 (세션 로그 대조)
□ 고도 없는 GPX 에서 E4 · E5 가 생략되는가 (폴백)
□ 웨이포인트가 경로 계산에 섞이지 않았는가
```

```

이번 발행은 Phase 3 착수 시점이며, 다음 통합판은 Phase 3 완료(G3) 시점이다.

## 정정 기록 — 로드맵 v2 §11 필수 상태 체크

**로드맵 v2는 D-055에 따라 개정하지 않는다. 이 절이 정정을 대신한다.**

```
등록되어 있던 것 (6)   purity, session-format, replay, negative-control,
                      replay-determinism, commit-trailer
미등록 (4)            core-guide-build, phase1-accuracy, config-sensitivity,

**미등록 4개는 실패해도 병합을 막지 못했다.** 엔진 빌드, 엔진 정확도, config 반응성, 엔진 반증 — Phase 3 엔진 변경에 가장 필요한 검사들이다.

```
G1 승인 시   필수 체크 등록 여부를 확인하지 않았다
로드맵 v2    9 개를 필수로 적으면서 실제 등록 상태와 대조하지 않았다
```

D-047(건수), D-049-c(작성자 신원)에 이어 **총괄이 확인 없이 단정한 세 번째 사례**다. D-028은 "등록은 워크플로 최초 실행 이후 소유자 조치"라고만 적었고, 등록이 실제로 이루어졌는지 확인하는 절차가 없었다.

### 조치 — 완료 (소유자 진술)

```
2026-09-21  소유자가 규칙 세트 main-protection 에 4개 추가 완료를 진술
```

**점검 에이전트는 다음 보고에서 규칙 세트를 조회해 10개 등록을 독립 확인한다.** 소유자 진술은 확인 대상이며 확인된 사실이 아니다(TASK-000 이래의 원칙).

```
게이트(G0 ~ G3) 판정 시 점검 에이전트는

```

"등록해야 한다"는 기록과 "등록되어 있다"는 사실은 다르다.

## D-056. 주기 설정과 이벤트 계열의 관계 — 안 1 채택, D-054 §2 보장 문장 정정

**상태**: 확정 | **일자**: 2026-09-21
**갱신 대상**: D-054 §2, §13 / 로드맵 v2 §7.2, §7.5

### 총괄 측 오류

D-054 §2와 §3은 서로 모순이었다.

```
§2   사용자가 정한 주기 설정이 전체 발화 빈도를 그대로 통제한다
     발화량은 늘지 않고 내용만 바뀐다
§3   교차형은 임계를 넘는 시점에 즉시 발화한다
```

그리고 **주기 음성의 기본값이 꺼짐**(`NavigationPreferences`: 켬 여부 false, 주기 0)임을 확인하지 않았다.

### 결정 — 안 1

```
(a) 주기 설정이 꺼져 있으면 E1 ~ E7 은 침묵한다
    이탈 · 꺾임 예고 · 온디맨드만 남는다
    단 E7 은 D-057 의 예외를 따른다

(b) 켜져 있으면 교차형은 즉시 발화하고 슬롯 타이머를 리셋한다
    (그 이벤트가 다음 슬롯을 대체한다)
    주기 계열 발화(E1 ~ E7 · 기본 문구) 사이 최소 간격 = 이벤트 최소 간격 (초기값 60초)

(c) G3 측정
    슬롯 발화의 간격 ≥ 주기 설정
    AND 주기 계열 발화 사이 간격 ≥ 최소 간격
```

### D-054 §2 보장 문장의 정정

**안 1에서도 "발화량은 늘지 않는다"는 문자 그대로 성립하지 않는다.** 5분 설정에서 교차형이 몰리면 5분에 여러 번 발화한다(최소 간격 60초까지).

```
정정 전   발화량은 늘지 않고 내용만 바뀐다
정정 후   사용자가 주기 설정을 켜야 이벤트 계열이 말한다      ← 켜짐/꺼짐 통제
         켜져 있어도 발화 간격은 최소 간격(60초) 미만이 되지 않는다 ← 빈도 상한
```

**약속을 과장하지 않는다.** 정정된 문장이 실제 동작과 일치한다.

### 안 2 · 안 3을 기각한 이유

```
안 2   기본 설정(주기 꺼짐)에서도 이정표 · 남은 거리가 들린다
       현재 대비 발화량 증가. "지루함을 고치려다 수다스러워지는" 실패
안 3   5분 설정에서 E3(종착 남은 거리)처럼 놓치면 가치가 큰 이벤트가 소멸
       D-054 §3.1 "E3 가 E1 보다 가치가 크다" 와 충돌
```

## D-057. E7(일몰까지 남은 시간)의 안전 예외 — 안 2 채택 및 보완 3건

**상태**: 확정 | **일자**: 2026-09-21
**갱신 대상**: D-054 §3.2, §7.2, §13 / 로드맵 v2 §7.3, §7.5

### 문제

E7은 교차형이라 임계를 넘는 순간에만 발화한다. 일반 억제 규칙을 그대로 적용하면:

```
이탈 중에 임계를 넘음       → 소멸. 다시 발화하지 않는다
시작 시 이미 30분 이내       → 넘을 임계가 없어 무발화
주기 설정 꺼짐 (기본값)      → 침묵 (D-056)
```

**어두워지는 시각에 경로를 벗어난 사용자가 일몰 안내를 영영 듣지 못한다.** 가장 필요한 상황에서 안전 기능이 꺼지는 구조다. 점검 에이전트의 지적이 정확하다.

### 결정 — 안 2

```
이탈 중에도 E7 은 발화한다. 이탈 안내가 우선하고 그 뒤에 이어서
시작 시 이미 임계 안이면 1 회 발화한다 ("일몰까지 25분입니다")
주기 설정이 꺼져 있어도 E7 은 발화한다
```

### 보완 1 — 소멸 금지 (안 2에 남아 있던 구멍)

안 2는 이탈 안내와의 충돌만 다룬다. 그러나 D-054 §7.2의 일반 규칙상 E7은:

```
꺾임 예고와 동시 발생   → 우선순위에서 밀려 버려진다
최소 간격에 걸림        → 버려진다
대기열이 없으므로       → 다시 발화하지 않는다
```

**결정:**

```
E7 은 버리지 않는다. 다음 발화 가능 시점까지 지연시킨다
이것이 D-054 §7.2 "대기열에 쌓지 않는다" 규칙의 유일한 예외다
```

**일반 억제 규칙이 안전 안내를 조용히 삼키는 경로가 이탈 외에도 두 개 더 있었다.** 규칙 표 구현 시 E7에 대해서만 "지연 허용, 소멸 금지" 속성을 둔다.

### 보완 2 — 명시적으로 끄면 존중한다

```
주기 설정 꺼짐          → E7 은 계속 발화한다 (암묵적으로 꺼지지 않는다)
E7 개별 설정 끔          → 따른다 (사용자의 명시적 선택)
기본값                  → 켬
```

**암묵적으로 꺼지는 것과 명시적으로 끄는 것은 다르다.** 안전 기능이라도 사용자가 직접 끈 것을 무시하지 않는다.

### 보완 3 — 이미 일몰 후에 시작한 경우

안 2는 "시작 시 이미 30분 이내면 1회"만 다룬다. **일몰이 이미 지난 뒤 시작하면 여전히 무발화다.**

```
시작 시 일몰 시각이 이미 지났으면 1 회 발화한다 ("일몰 시각이 지났습니다")
```

### 발화 상한

```
세션당 최대   임계 발화 2 회 (60분 전 · 30분 전)
             + 시작 시 1 회 (임계 안 또는 일몰 후)
```

### 억제 규칙에서의 E7 위치 — 정리

| 억제 조건 | E1~E6 | E7 |
|---|---|---|
| 이탈 중 | 중단 | **발화** (이탈 안내 뒤) |
| 역방향 진행 | E1·E3·E4·E6 중단 | 발화 |
| 신호 불량 | "경로 위" 계열 자제 | 발화 (경로 위 계열 아님) |
| 주기 설정 꺼짐 | 침묵 | **발화** |
| 개별 설정 끔 | 침묵 | 침묵 |
| 동시 발생 · 최소 간격 | 버림 | **지연** (소멸 금지) |

## 승인 사항 (결정 아님, 기록)

### 규칙 표 구조 — 승인

억제 대상, 주기 꺼짐 시 동작, 발화 간격 상한을 **규칙 표 하나에서 바꿀 수 있는 구조**로 구현하게 한 지시를 승인한다. 이번처럼 규칙이 바뀌어도 표만 갱신하면 된다.

E7의 "지연 허용, 소멸 금지" 속성도 같은 표에 둔다.

### 부록 B — 비식별 스캐너에 경로 고도와 웨이포인트 이름 추가 — 승인

```
경로 고도       D-054 §11
웨이포인트 이름  장소명 — 고도 프로파일과 같은 식별 위험
```

**총괄이 D-054 §11에서 고도만 짚고 장소명을 놓쳤다.** 점검 에이전트가 보완했다. D-053 §2.2에 따라 각각 위반 입력을 함께 둔다.

### 부록 C — 검사 실패 출력 규약 — 승인

```
새 검사의 실패 출력에 "FAIL: <원인>" 한 줄을 반드시 포함한다
```

D-053의 연장이다. **추출기가 아무리 정확해도 검사가 원인을 출력하지 않으면 원인을 뽑을 수 없다.** 첫 `failrec-2.0.1` 기록 3건 중 1건이 약했던 이유가 이것이었다(추출기 결함 아님).
