## D-001. 이탈 임계값 네임스페이스 분리

**상태**: 확정 | **일자**: 2026-09-13

### 배경

두 문서가 같은 이름으로 다른 값을 쓰고 있었다.

```
로깅 스킬 §6 / session_schema tags   OFF_ROUTE = 30m + 60초
MVP 계획 §4.1                        진입 25m/20초, 해제 15m/10초
```

오류가 아니라 용도가 다른 값이다. 그러나 이름이 같으면 구현 에이전트가 반드시 하나로 통합하려 든다.

### 결정

네임스페이스를 분리한다. 값은 서로 독립이며 튜닝도 따로 한다.

```
guide.offRoute.*        실시간 안내용
  enterDist 25m / enterDwell 20s
  exitDist  15m / exitDwell  10s
  근거: 사용자 체감 기준. 늦게 알리면 이미 멀리 간 뒤다

tagging.OFF_ROUTE.*     사후 태깅용
  dist 30m / dwell 60s
  근거: 관심 구간 과다 생성 방지. 보수적으로 둔다
```

### 시행

- 엔진 config와 태거 config를 분리된 키로 둔다
- 두 값 모두 코드 상수 금지. config에서 읽는다 (로깅 스킬 §6)

## D-002. 반증 테스트 용어 교체

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 §2.2, §4(4)가 **음성(陰性) 대조 = negative control**을 요구한다. 검사기가 통과시키는 것만 확인하면 아무것도 검사하지 않는 검사기와 구별되지 않으므로, 고의 위반을 주입해 실제로 기각되는지 확인하라는 규율이다.

문제는 용어다. 이 프로젝트는 TTS 음성 안내가 핵심 기능이고, 로그에 `tts`·`stt` 스트림이 있으며, 문서 전반에 "음성 안내", "발화"가 나온다. 그 한가운데 "음성 대조"를 놓으면 구현 에이전트가 **TTS 출력 비교 작업**으로 오해할 소지가 크다. 실제로 "기록된 발화와 리플레이 발화를 대조한다"는 작업이 이 프로젝트에 실재하므로, 그럴듯한 오해다.

### 결정

```
음성 대조  →  반증 테스트 (negative control)
```

관리 지시서 §2.2, §4(4) 두 곳. 이후 모든 문서에서 "반증 테스트"로 통일한다.

### 근거

설계 변경이 아니라 지시가 오독될 여지를 막는 수정이다. 오독되면 검증 체계 전체가 헛돈다.

## D-003. 검증 계층 공백 — 판정 주체를 기계로 이전

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 §4는 구현 에이전트의 보고를 5개 요건으로 검증한다. 그러나 **검증 에이전트의 판정 자체를 검증할 주체가 없다.**

```
구현 에이전트 → 보고 → 검증 에이전트 → 판정 → ???
```

검증 에이전트가 "반증 테스트 완료, exit 1 확인"이라고 쓰면 그것을 확인할 방법이 없다. §4(3)이 경고한 사고 — 검사 하네스가 자기 입력을 매칭하고 "확인됨"으로 보고한 일 — 가 한 층 위에서 재현될 수 있다.

상위 감사자를 계속 쌓는 것은 해가 아니다. 무한히 올라간다. 사람이 매번 감사하는 방식도 실패한다 — 로깅 가이드 §1.1이 이미 적었다. 자발적 기록과 사람 의존 규율은 반드시 중단된다.

### 결정

감사 계층을 늘리지 않는다. **검증 에이전트가 주관적으로 판정하던 항목을 CI로 옮겨 판정 주체를 기계로 바꾼다.**

#### D-003a. 반증 테스트를 CI 잡으로

수동 수행 + 보고 방식을 폐기한다. 고의 위반 픽스처를 저장소에 두고 CI가 매번 돌린다.

```
testdata/violations/
  engine_impure_clock.kt.txt      System.currentTimeMillis() 포함
  engine_impure_random.kt.txt     Math.random() 포함
  session_seq_regress/            seq 역행
  session_missing_manifest/       매니페스트 누락

guard.yml 잡 추가: negative-control
  각 픽스처에 검사기를 돌려 exit 1 을 확인
  exit 0 이면 이 잡이 실패한다
```

픽스처는 컴파일 대상에서 제외한다(`.kt.txt` 확장자). 빌드가 깨지면 안 된다.

#### D-003b. 리플레이 자기 대조를 CI 잡으로

```
guard.yml 잡 추가: replay-determinism
  동일 세션을 2회 리플레이해 서로 비교
  불일치 = 비결정성 확정
```

기록과 비교하는 기존 `replay` 잡은 기록 자체가 오염됐으면 통과한다. 자기 자신과 비교하는 방식은 그 구멍이 없다.

정적 순수성 검사는 래퍼 경유 간접 호출을 잡지 못한다(관리 지시서 §2.1이 이미 인정). **진짜 판정기는 리플레이다.** 정적 검사는 1차 필터로 남긴다.

작동 조건: 골든 세션 1개로는 부족하다. 시계·난수 의존은 특정 조건에서만 드러난다. 합성 세션(노이즈 3단계 × 이탈 3종)을 전부 대상에 넣는다.

#### D-003c. 필수 상태 체크를 5개로

```
purity
session-format
replay
negative-control      ← 추가
replay-determinism    ← 추가
```

#### D-003d. 검증 에이전트에게 남는 것

```
남는 것   보고와 커밋 SHA 대조
          구현이 검사를 우회하는 방향으로 가는지 판단
          엔진 패키지 경계 감시
          게이트 통과 판정

빠지는 것  검사기가 작동하는지 확인 → CI가 한다
```

검증 에이전트의 신뢰성을 높이는 것보다, **신뢰받아야 할 범위를 줄이는 편이 확실하다.**

#### D-003e. 판단 영역은 숫자 추이로 노출

경계 감시는 여전히 사람/에이전트 판단이다. 서술이 아니라 지표로 보고하게 한다. 관리 지시서 §8 주기 보고에 추가한다.

```
엔진 패키지 파일 수 / LOC
엔진 외부 헬퍼 LOC (엔진이 호출하는 유틸)
```

엔진 LOC가 줄면서 외부 헬퍼가 늘면 **경계를 밖으로 밀어낸 것**이다. 정적 검사가 못 잡는 우회의 대리 지표다. 서술로는 숨길 수 있으나 숫자 추이는 숨기기 어렵다.

#### D-003f. 소유자 감사는 조건부

매번 감사는 지속되지 않는다. 세 조건에서만 확인을 요청한다.

```
필수 체크를 해제·완화하려 할 때 (지시서 §5 "푸는 변경")
게이트 통과 선언 시점 (G0~G3, 4회)
검사기가 잡은 위반 건수가 4주 연속 0일 때
```

마지막 항목이 §8의 "0이면 검사기를 의심한다"를 실행 가능한 트리거로 바꾼 것이다.

### 부작용

G0 작업량이 늘어난다. 픽스처 4종 + CI 잡 2개. 전부 코드 0줄일 때 만드는 것이라 지금이 가장 싸다.

## D-004. 세션 스키마 v1 동결 범위 한정

**상태**: 확정 | **일자**: 2026-09-13

### 배경

관리 지시서 G2는 실제 산행 1회 후 스키마를 v1으로 동결한다고 한다. 그런데 `session_schema.json` v0에는 `ar`, `stt` 스트림이 이미 정의되어 있고, MVP 계획상 AR 화살표는 Phase 4, STT는 범위 밖이다.

즉 **v1 동결 시점에 `ar`·`stt`는 한 번도 실측되지 않은 채 동결된다.** 로깅 스킬 §8.1의 "실측 없이 스키마를 정교하게 만들지 않는다"와 정면으로 어긋난다.

### 결정

```
동결 대상    manifest, event_envelope, loc, guide, sys, err
미동결 유지  imu, baro, ar, stt   ← "실험 스트림"으로 명시
```

실험 스트림은 `validate_session.py` 필수 검사 대상에서 제외한다.

### 근거

리플레이가 대조하는 것은 `guide` 스트림뿐이다. 나머지는 입력이거나 부수 기록이므로 전부 동결할 이유가 없다. 실측되지 않은 스트림을 동결하면 추측을 규격으로 굳히게 된다.

## D-005. AKB 공급 계약 확정

**상태**: 확정 | **일자**: 2026-09-13
**근거 문서**: `xchg/akb-tnapp/XCHG-001`, `XCHG-002`, `XCHG-003`

### 결정

AKB 총괄 요청 4건을 전부 수용했다. 계약이 성립했다.

```
공급   빌드 실패 레코드 / 실패↔수정 쌍 / 검사기 기각 이력
비제공 런타임 산행 세션 로그 / 안전 사건 기록 / AKB 형식 가공
조건   단방향, 통지 의무 없음, tnApp 단독 중단권, 범위 한정
```

### 수용한 확장 4건

| 항목 | 내용 | 비용 |
|---|---|---|
| `runner_image_version` | 러너 환경변수 그대로 | 필드 1 |
| `schema_version` | `failrec-` 접두. 소비 측 자력 감지용 | 필드 1 |
| 커밋 원자성 | Failed-Run 커밋에 다른 변경 혼입 금지 | 리뷰 규칙 |
| 해소 확인 기록 | 수정 후 실제 통과 증거 | 필드 4 + CI 스텝 1 |

### 해소 확인 기록 — 구현 방식 변경

AKB 제안(실패 시점에서 후속 성공 추적)은 `workflow_run` 트리거 구조상 상태 보유나 역방향 조회가 필요하다. **성공 시점에서 뒤를 보는 방향으로 뒤집는다.**

```
guard 성공 시
  HEAD 커밋에 Failed-Run: 트레일러가 있는가
  있으면 → 실패 레코드에 해소 레코드를 append (원본 수정 아님)
    resolved_by_commit / resolved_run_id / resolved_at
```

`check_commit_trailer.py`의 트레일러 파싱을 재사용한다.

**이 결정은 AKB를 위한 것만이 아니다.** 관리 지시서 §4는 구현 에이전트에게 "실제로 실행됐다는 증거"를 요구하면서, 정작 수정이 실패를 해소했다는 증거는 요구하지 않았다. AKB 요청이 tnApp 자신의 규율 공백을 짚었다.

**부수 효과**: 해소 필드가 끝내 채워지지 않은 레코드가 남는다. "고쳤다고 커밋했으나 통과하지 못한" 사례가 별도 작업 없이 분리된다.

### error_signature — 정규화하지 않는다

원문 보존. 정규화·마스킹·해시는 소비 시점 처리. 정규화가 비가역이며, D1에서 재설계가 가능했던 유일한 이유가 원문 보존이었다는 AKB 근거를 수용했다.

예외는 비밀정보 마스킹뿐이며, `masking_ruleset_version`을 함께 기록한다. 마스킹도 비가역이므로 어떤 비가역 처리가 가해졌는지는 남겨야 한다.

### 향후 범위 확대 시 우선 검토 항목

**`negative-control` 픽스처를 AKB 홀드아웃 재료로 제공하는 안.**

AKB D1에서 `pathological` 사례가 530건 중 0건이었고 야생에 존재하지 않는 종류라면, 통제된 환경에서 의도적으로 만드는 것 외에 경로가 없다. D-003a의 픽스처가 그 성격에 가깝다 — 고의 주입 위반이며, 검사기가 기각해야 정상인 사례다.

**이번 계약에 포함하지 않는다.** AKB가 별도 문서로 제기하면 검토한다.

### AKB 재개 미정 상태에 대한 판단

AKB S0-R은 2026-09-13 미도달 종료, 재개 미정이다. 이를 인지하고 수용했다.

```

tnApp에도 필요했다   해소 확인 기록은 자체 규율 공백이었다
소급이 불가능하다    지금 넣지 않으면 6개월 뒤에도 없다
```

## 이 문서가 분리된 이유

드라이브는 기존 파일에 append가 불가능합니다. 매번 전체를 다시 올리면 append-only 원칙이 형식만 남으므로, 분책으로 처리합니다.

**저장소에 `docs/DECISIONS.md`가 만들어지면 두 문서를 병합해 이관합니다.** git이 append-only를 구조적으로 보장하고, force push 금지가 걸려 있어 소급 수정도 막힙니다. 드라이브 사본은 그 시점부터 참조용입니다.

## D-006. 저장소 및 자격증명 구성

```
1순위  브랜치 보호가 실제로 작동할 것
2순위  프라이빗
```

```
ruleset   main-protection (id 23165335), enforcement active
bypass_actors   비어 있음. current_user_can_bypass: never
rules   deletion / non_fast_forward / pull_request
pull_request 파라미터
  required_approving_review_count: 0
    → 1인 개발 구조. GitHub 은 작성자가 자기 PR 을 승인할 수 없으므로

```

**bypass 목록을 비워둔 것이 핵심입니다.** admin 을 bypass 에 넣으면 force push 차단 검증이 통과해버립니다 — 검사기가 자기를 통과시키는 것과 같습니다.

/sessions/

```

`.gitignore`는 실수를 막을 뿐이며 `git add -f`로 우회됩니다. 규율이 함께 필요합니다.

### PAT

```

  종류    Fine-grained PAT
  대상    tnapp-failure-log 단일
  권한    Contents: Read and write (+ Metadata: Read-only, 자동)

퍼블릭 저장소이므로 포크 PR이 들어올 수 있습니다. `workflow_run` 트리거 잡은 시크릿과 쓰기 권한을 가진 채 base 컨텍스트에서 실행됩니다.

```

## D-007. TASK-000 판정 기준 정정 — 실패와 수행 불가의 구분

**상태**: 확정 | **일자**: 2026-09-13

TASK-000 지시서 §6은 "4.4(force push 반증 테스트) 실패는 단독으로 착수 불가"라고 규정했습니다. **실패와 수행 불가를 구분하지 않은 지시서의 결함입니다.**

```
실패       force push 를 시도했는데 성공했다 → 보호 미작동. 착수 불가
수행 불가   main 브랜치가 없어 시도 자체를 못 했다 → 정보 없음
```

빈 저장소에 main이 없는 것은 당연하며, main은 최초 커밋으로 생기고, 최초 커밋은 G0 작업의 일부입니다. 착수 전 관문으로 두면 순환이 되어 영원히 착수할 수 없습니다.

**4.4는 로드맵 §3.4-2(G0 완료 판정)의 원위치로 되돌립니다.**

점검 에이전트가 이 충돌을 임의 해석하지 않고 그대로 보고한 것은 올바른 처리였습니다.

## D-008. 인증 확보 후에도 점검 에이전트는 읽기 전용

## D-009. 커밋 이메일 — noreply 주소 사용

**상태**: 확정 | **일자**: 2026-09-13

브랜치 보호의 `require_extra_approval_for_unattributed_changes`가 기본값 `true`로 설정되어 있습니다. GitHub 계정에 연결되지 않은 커밋이 PR에 포함되면 추가 승인을 요구하며, 승인 수가 0이어도 발동합니다.

```
git config user.email "<ID>+twenione@users.noreply.github.com"
```

noreply 주소는 정의상 계정에 연결되어 있으므로 이 조건이 발생하지 않습니다. 실제 이메일을 공개 저장소의 커밋 이력에 남기지 않는 부수 이득도 있습니다.

**규칙 파라미터를 끄는 방안은 채택하지 않았습니다.** 실제로 막히는지 확인되지도 않은 상태에서 규칙부터 푸는 것은 순서가 틀렸고, 푸는 변경은 관리 지시서 §5 대상입니다.

## D-011. 현장 테스트를 G2-a / G2-b로 분리

**상태**: 확정 | **일자**: 2026-09-13

실제 산행은 3시간 이상이 소요되어 개발 루프에 넣을 수 없습니다. 소유자가 자택 인근에 테스트 경로를 확보했으며, 갈림길이 복수 존재합니다.

```
G2-a  동네 경로 테스트
      기능 동작 확인, 서비스 생존, 배터리 실측, UI 조작성
      반복 가능. 개발 루프에 포함

G2-b  실제 산행 1회
      GPS 품질 실측, 파라미터 검증
      스키마 v1 동결 조건
```

### 동네 테스트로 검증되지 않는 것

```
수목 밀집 구간 GPS 품질 (이 앱의 난이도 대부분이 여기 있다)
계곡 · 능선 사면의 멀티패스
통신 두절 상태
철 성분 암반에 의한 나침반 오차
```

**따라서 동네 테스트로 파라미터를 튜닝하지 않습니다.** 개활지에서는 오차가 5m 안쪽으로 나오므로 이탈 임계 25m가 과해 보이고 줄이고 싶어집니다. 그 상태로 산에 가면 오탐이 쏟아집니다.

스키마 동결을 G2-b에 묶어두는 이유도 같습니다. 동네 데이터만 보고 굳히면 산에서 필요한 필드를 놓칩니다.

### 기준 경로 고정

같은 경로를 반복해 걷는 것이 전제입니다. 매번 다른 곳을 걸으면 회차 간 비교가 불가능합니다. 세션 로그의 `gpx_hash`가 경로 동일성을 보장합니다 — 경로 파일이 바뀌면 해시가 달라지므로 다른 경로의 결과를 섞어 비교하는 실수가 걸러집니다.

### 분기점 사전 기록

테스트 판정을 위해 소유자가 분기점 목록을 사전 작성합니다.

```
위치 / 분기 각도(눈대중) / 정답 방향 / 형태
형태 = 꺾임형(정답이 꺾임) 또는 직진형(정답이 직진, 옆길이 갈라짐)
```

**직진형 분기는 GPX상 방위각 변화가 0이므로 꺾임 예고가 원리적으로 불가능합니다.** 사전 분류하지 않으면 테스트에서 이를 결함으로 오인 보고하게 됩니다. 알려진 한계이며, 이탈 감지 성능 실측에 사용합니다.

## D-013. 필수 상태 체크를 6개로 — `commit-trailer` 포함

## D-014. 해소 레코드 `run_id`는 원본 실패의 ID

**상태**: 확정 | **일자**: 2026-09-13
**근거**: `TASK-003_DECISION_REQUEST_2026-09-13.md` D-R9

### 상황

PR #9 병합 후 생성된 해소 레코드 3건 전부에서 `run_id`가 `resolved_run_id`와 동일한 값이었습니다. 원본 실패 run(`34761334020`, `34761342131`)은 해소 레코드 어디에도 나타나지 않습니다.

### 결정 — 점검 의견 (a) 채택. 현행 구현은 사양 위반입니다

스키마 설명이 부실했던 것은 총괄 책임이나, 필드 의미는 원래 (a)였습니다.

```
run_id               해소된 원본 실패의 run_id
resolved_by_commit   수정 커밋 SHA
resolved_run_id      해소를 확정한 성공 run 의 id
resolved_at          타임스탬프
```

**근거 1 — 스키마 구조.** `resolved_` 접두가 붙은 세 필드가 "해소 쪽" 정보이고, 접두 없는 `run_id`는 그 대칭으로 "해소된 쪽"입니다. 접두를 붙인 이유가 그것 외에 없습니다. 현행 구현에서는 두 필드가 항상 같으므로 하나가 순수한 중복입니다.

**근거 2 — AKB 계약 구조.** AKB는 `tnapp-failure-log`만 읽습니다. 앱 저장소의 커밋 메시지를 조회할 권한이 계약에 없습니다. `resolved_by_commit`에서 트레일러를 역추적하려면 두 저장소를 모두 봐야 하는데, **단방향 읽기 계약에서 그것이 성립하지 않습니다.** 레코드만으로 연결이 닫혀야 합니다.

### 기존 레코드 처리

**이미 생성된 3건은 수정하지 않습니다.** append-only 원칙이 우선합니다. 수정 이후 레코드부터 새 형식이 적용되며, 형식이 갈리는 구간이 존재한다는 사실을 이 기록으로 남깁니다.

구현은 `check_commit_trailer.py`의 기존 트레일러 파싱 로직을 재사용합니다.

## D-015. 해소 레코드는 `main` push 성공 시에만 append

**상태**: 확정 | **일자**: 2026-09-13
**근거**: `TASK-003_DECISION_REQUEST_2026-09-13.md` D-R10

### 상황

동일한 수정 1건(커밋 `2f918c7`)에 대해 해소 레코드가 3개 생성되었습니다 — PR 브랜치 성공 2회(push 트리거, pull_request 트리거) + main 병합 후 push 트리거 1회.

### 결정 — 점검 의견 (b) 채택

```
guard 성공 + 트리거가 main push + HEAD 에 Failed-Run: 트레일러
→ 해소 레코드 append
```

**PR 단계의 성공은 해소가 아닙니다.** 이후 커밋이 추가되면 뒤집힐 수 있는 상태를 "해소됨"으로 기록하면 그 레코드가 거짓이 될 수 있습니다.

해소 레코드의 가치는 "고쳤다는 주장"이 아니라 **"고쳐진 것이 확정됐다"는 증거**입니다. main 병합이 그 확정 시점입니다.

**부수 효과**: 중복이 사라지면 미해소 잔존 레코드를 세는 것이 의미를 갖습니다. 한 수정에 3건이 붙으면 주간 보고의 "해소 확인률"이 왜곡됩니다.

### 17-a. 합성 세션 기준 경로 — 익명화본을 저장소에 커밋

오프셋 값과 원본 GPX 는 저장소에 넣지 않는다
```

저장소에 남는 것은 위치 정보가 아니라 형상뿐이며, 원본과 대조할 수단이 없으면 복원이 불가능합니다. 오프셋은 일회성 변환이므로 재사용할 일도 없어집니다.

```
스텁 엔진은 결정론적이기만 하면 된다
예: 입력 프레임 수를 세어 고정 규칙으로 출력을 생성
안내 로직을 구현하지 않는다 — Phase 1 범위다
```

PR-6의 목적은 **리플레이 경로가 존재하는 것**이지 엔진이 아닙니다.

### 17-c. 앱 빌드 잡 Phase 0 제외 — 점검 의견 승인

관리 지시서 §3.2의 `assembleDebug`/`testDebugUnitTest` 잡을 Phase 0에서 제외한 판단을 승인합니다.

`:app`이 빈 스켈레톤이면 이 잡은 실패할 일이 없습니다. **검사기가 무언가를 잡는지 확인할 수 없는 잡을 넣으면 항상 초록불인 체크가 하나 생깁니다.** 함정 목록의 "아무것도 안 잡는 negative-control"과 같은 성질입니다.

## D-018. 점검 범위에 산출물 실질 검토를 포함

**상태**: 확정 | **일자**: 2026-09-14

### 상황

AKB 조회가 구현 결함 4건을 짚어냈습니다.

```
toolchain 전 필드 빈 문자열 — 추출 로직 부재
failed_task 가 워크플로 이름("guard")으로 고정 — 잡 구분 없음
빈 로그 레코드(log:"")가 스키마를 통과해 정상 커밋됨
log_ref 가 존재하지 않는 logs/ 디렉터리를 가리킴
```

**전부 tnApp 점검 에이전트가 먼저 잡았어야 할 것들입니다.** 특히 빈 로그와 무효 `log_ref`는 레코드 파일을 한 번 열어보면 드러납니다.

### 원인 진단

점검이 실패한 것이 아니라, **점검 범위가 형식에 한정되어 있었습니다.**

```
검증한 것   PR 별 완료 정의 충족 여부
            명령이 실행되었는가, 종료 코드가 기대와 같은가
            증거가 원문으로 첨부되었는가

검증하지 않은 것
            산출물의 내용이 쓸 만한가
            선언한 필드에 실제 값이 들어 있는가
            참조가 실제로 가리키는 곳이 있는가
```

워크플로가 "정상 종료"하고 레코드가 "생성"되었으므로 형식 기준으로는 전부 통과입니다. **그러나 생성된 레코드는 절반이 비어 있었습니다.**

이는 D-003에서 다룬 문제의 변형입니다. 검사기가 아무것도 검사하지 않으면서 초록불을 내는 상황과 같은 구조이며, 이번에는 검사 대상이 검사기가 아니라 산출물이었습니다.

### 결정

**점검 에이전트의 검증 항목에 산출물 실질 검토를 추가합니다.**

```
기록 계열 산출물(레코드, 세션 로그, 스키마 인스턴스)이 생성되면
1. 실제 파일을 열어 내용을 확인한다
2. 선언된 모든 필드에 유효한 값이 있는지 본다
   빈 문자열 · null · 하드코딩 상수는 결함으로 간주한다
3. 참조 필드(경로, ID)가 실제로 가리키는 대상이 존재하는지 확인한다
4. 동일 필드가 복수 레코드에서 항상 같은 값이면 하드코딩을 의심한다
```

4번이 이번 사례의 핵심 탐지 조건입니다. `toolchain`과 `failed_task`가 3건 전부 동일했던 것이 신호였습니다.

**"생성되었다"는 완료 정의로 불충분합니다.** 앞으로 작업 지시서의 완료 정의에는 산출물 내용에 대한 조건을 포함시킵니다.

## D-019. `toolchain` 실제 추출

**상태**: 확정 | **일자**: 2026-09-14

## D-020. `failed_task`를 실패한 잡 이름으로 기록

**상태**: 확정 | **일자**: 2026-09-14
**근거**: AKB Q2

`"guard"`는 워크플로 이름이며 정보량이 거의 없습니다. `guard.yml`은 6개 잡으로 구성되어 있고, 그 여섯은 성격이 다릅니다.

```
purity / session-format / replay / commit-trailer   검사기 기각 이력
negative-control / replay-determinism               검사기 자체의 고장 신호
(Phase 2 이후) 빌드 태스크                            빌드 실패
```

**두 번째 줄이 특히 구분되어야 합니다.** `negative-control` 실패는 코드 결함이 아니라 **검사기가 위반을 더 이상 잡지 못하게 됐다**는 신호입니다. 이것이 코드 실패와 같은 값으로 기록되면 D-003에서 세운 감시 구조가 보이지 않게 됩니다.

XCHG-001 §2.3이 검사기 기각 이력을 별도 공급 항목으로 규정했으므로, 현 형태는 계약 미충족이기도 합니다.

복수 잡 동시 실패 시의 표기(단일 문자열 vs 배열)는 구현 재량으로 둡니다. 결정 후 점검 에이전트가 기록하십시오.

## D-021. 빈 로그 레코드를 커밋하지 않음

**상태**: 확정 | **일자**: 2026-09-14
**근거**: AKB Q3

### 결정

```
log_sha256 == e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  (빈 문자열의 SHA256)
→ 레코드를 커밋하지 않고 워크플로를 실패시킨다
```

### 근거 — AKB 편의가 아니라 tnApp 자신의 문제

이 항목은 AKB 소비 편의가 아니라 **tnApp의 감지 체계가 무력화되는 경로**입니다.

주간 보고에 "마지막 실패 레코드 기록 일시"를 둔 목적은 기록 체계가 멈춘 것을 감지하기 위해서였습니다(토큰 만료, 워크플로 고장). 그런데 **빈 레코드가 계속 커밋되면 그 지표가 계속 갱신됩니다.** 체계가 죽었는데 살아 있는 것으로 보입니다.

누락된 레코드는 API 목록과 대조하면 드러납니다. 반면 빈 레코드는 스키마를 통과해 정상 레코드로 계수됩니다. **"레코드 3건"이 실제로는 1건인 상태**가 만들어집니다.

### 구현 시 유의

**재귀 위험**: 실패 보존 워크플로 자신의 실패가 다시 자신을 호출하는 경로를 차단해야 합니다. 빈 로그로 워크플로를 실패시킬 때 이 경로를 함께 검토하십시오.

## D-023. `schema_version` 상향 및 형식 경계 명시

**상태**: 확정 | **일자**: 2026-09-14

D-014, D-015, D-019~D-022가 레코드 형식을 변경하므로 `schema_version`을 올립니다.

### 기존 레코드는 수정하지 않습니다

append-only 원칙이 우선합니다. 원본을 고치면 "그 시점에 무엇이 기록됐는가"가 훼손되며, 이는 tnApp 기록 체계의 근간입니다.

**따라서 형식이 갈리는 구간이 저장소에 영구히 남습니다.**

```
수정 이전   toolchain 빈 문자열, failed_task="guard", log_ref 무효,
           resolution run_id 중복, 해소 레코드 3중 생성, 일부 빈 로그
수정 이후   위 항목 전부 정상
경계        schema_version 으로 구분
```

이것은 결함이 아니라 append-only의 대가입니다. 소비 측은 `schema_version`으로 분기 처리합니다.

`schema_version`을 채택한 이유가 여기서 실증되었습니다 — 통지 의무 없이 소비 측이 변경을 자력 감지하는 경로입니다.

## D-024. D-015 트리거 조건 정정 — `HEAD`가 아니라 push 커밋 범위

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-015
**근거**: AKB `XCHG-006` §2.1

### 결함

D-015는 다음과 같이 규정했습니다.

```
guard 성공 + 트리거가 main push + HEAD 에 Failed-Run: 트레일러
→ 해소 레코드 append
```

**`HEAD`를 보는 부분이 오류입니다.** 병합 전략에 따라 트레일러가 HEAD에 없습니다.

```
merge commit   HEAD = "Merge pull request #N from ..."
               트레일러는 부모 커밋에 있고 HEAD 에는 없다

squash merge   기본 메시지가 PR 제목 + 본문에서 합성됨
               원 커밋의 트레일러가 유실될 수 있다

rebase merge   마지막 커밋에 트레일러가 없으면 찾지 못한다
```

D-006에서 merge commit과 squash를 **둘 다 허용**해 두었으므로, 이 취약점이 발동할 조건이 이미 갖춰져 있었습니다.

### 실패 양상이 더 나쁩니다

```
빈 레코드(D-021)   저장소에 보인다. 세면 드러난다
해소 0건           아무것도 남지 않는다. 워크플로는 정상 종료한다
```

같은 계열의 문제이며, **이쪽이 더 보이지 않습니다.** D-021을 결정하면서 바로 옆의 D-015에 같은 함정을 만들어 둔 셈입니다.

### 결정

```
guard 성공 + 트리거가 main push
→ push 이벤트의 커밋 범위 전체를 훑는다
   payload.commits[] 또는 before..after 범위
→ Failed-Run: 트레일러를 가진 커밋을 찾아 해소 레코드 append
```

병합 전략과 무관해집니다.

**D-015의 판단 자체는 유지됩니다.** PR 단계의 성공은 이후 커밋으로 뒤집힐 수 있으므로 main 병합 시점에만 기록한다는 근거는 그대로입니다. 바뀌는 것은 **어디서 트레일러를 찾는가**뿐입니다.

### 검증 요건 추가

수정 실증 시 **병합 전략별로 확인**하십시오. 한 가지 전략에서만 확인하면 나머지에서 0건이 되는 상태를 놓칩니다.

## D-025. `failed_jobs` — 배열로 고정, 필드명 변경

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-020
**근거**: AKB `XCHG-006` §2.2

### 결정

D-020에서 구현 재량으로 미뤘던 표기 방식을 총괄이 확정합니다.

```
필드명   failed_task  →  failed_jobs
형식     항상 배열. 1건일 때도 배열
예       "failed_jobs": ["purity"]
         "failed_jobs": ["purity", "replay"]
```

### 근거

**`guard`의 6개 잡은 병렬 실행입니다.** 한 run에서 둘 이상 실패하는 것은 비정상이 아니라 정상입니다. 단일 문자열이면 정보가 사라집니다.

**타입이 상황에 따라 바뀌는 것이 더 나쁩니다.** 1건일 때 문자열, 2건 이상일 때 배열이면 소비 측이 매번 분기해야 하고, 그 분기를 빠뜨리면 조용히 틀립니다.

필드명을 복수형으로 바꾸는 이유는 **이름이 타입을 드러내게** 하기 위해서입니다. `failed_task`라는 이름은 단수를 암시해 소비 측의 오해를 부릅니다. 어차피 `schema_version`이 올라가는 사이클이므로 지금이 바꿀 시점입니다.

## D-026. `toolchain` — 값의 출처를 레코드에 명시

**상태**: 확정 | **일자**: 2026-09-14
**갱신 대상**: D-019
**근거**: AKB `XCHG-006` §2.3

### 배경

D-019는 "CI 실행 시점에 실제 추출"이라고만 규정했습니다. 그러나 실제로는 두 종류가 섞입니다.

```
실행 산출값   java -version, gradlew --version 등의 출력
             그 버전으로 실제로 돌았다는 증거

파일 선언값   libs.versions.toml, gradle-wrapper.properties
             그 버전을 쓴다고 적혀 있었다는 기록
```

AGP는 실행값을 얻기 어려워 선언값이 될 것이고, 그 자체는 문제가 아닙니다. **섞여서 구분이 안 되는 것이 문제입니다.** 소비 측이 판정에 쓸 때 두 값의 증거 강도가 다릅니다.

### 결정

**값 자체에 출처를 붙입니다.**

```json
"toolchain": {
  "gradle": { "value": "8.x", "source": "runtime" },
  "jdk":    { "value": "17.x", "source": "runtime" },
  "agp":    { "value": "8.x", "source": "declared" },
  "kotlin": { "value": "2.x", "source": "declared" },
  "ndk":    { "value": "",    "source": "unavailable" }
}
```

```
source 값
  runtime      실행 산출값
  declared     파일 선언값
  unavailable  둘 다 얻지 못함 (값은 빈 문자열)
```

### 구현 방식을 이렇게 정한 이유

```
필드를 나누는 방식        소비 측이 두 곳을 봐야 한다
스키마 문서에만 적는 방식   레코드만 보는 쪽이 놓친다
```

**레코드가 자기 증거 강도를 스스로 밝히는 형태**가 낫습니다. 문서를 참조하지 않고도 판정이 가능합니다.

`unavailable`을 명시적 값으로 둔 이유는 D-018 때문입니다. 빈 문자열만 있으면 "추출 실패"인지 "해당 없음"인지 구분되지 않고, 그것이 이번 사이클에서 고치는 결함의 원인이었습니다.

### 근거 — AKB S0-R 구조적 발견 6번

AKB는 로그 텍스트에서 추측한 값으로 로그 텍스트를 판정했고, 그것이 S0-R 후반부 전체를 관통한 결함이었습니다. **선언값과 실행값을 섞으면 tnApp이 같은 함정에 들어갑니다.**

`toolchain`을 채우기로 한 애초의 근거가 "tnApp은 자기 CI가 무엇을 돌렸는지 이미 안다"는 독립성이었습니다. 출처를 구분하지 않으면 그 독립성이 절반만 성립합니다.

## 이월 — Phase 1 검토 항목

AKB가 `XCHG-006` §5에서 S0-R 사례 하나를 공유했습니다.

```
screening 규칙 YAML v2 를 선언하고 declared_rule_sha256 도 일치했으나
실행 코드는 정적 v1 딕셔너리를 쓰고 있었다
형식 검사는 전부 통과했고, 측정 한 회차가 통째로 무효가 됐다
```

**tnApp의 리플레이 체계에도 같은 구조가 가능합니다.** `engine_config` 해시가 일치해도, 엔진이 그 config를 실제로 읽고 있는지는 별개 문제입니다. 코드 상수가 config를 덮어쓰고 있어도 해시는 일치합니다.

**이번 사이클에서는 다루지 않습니다.** 엔진이 아직 없습니다.

**Phase 1 작업 지시서 작성 시 점검 에이전트가 이 각도를 검토하십시오.** 구체적으로는 "config 값을 바꾸면 엔진 출력이 실제로 달라지는가"를 확인하는 경로가 필요합니다. 이것도 반증 테스트의 한 형태입니다.
